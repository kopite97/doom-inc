# PLAN-009 가공·배양·보급형 운용과 시스템 책임·명명 정비

## 목표

PLAN-008의 실제 초기 건설·수집·저장에서 이어서 가공시설과 공용 배양시설을 건설하고, 배양액 생산·입고 → 생명체 배양 → 보급형 배정으로 생산을 개선하는 흐름을 구현한다.
첫 보급형 없이도 20% 자동 생산으로 진입할 수 있고, 실제 작업 중 100% 전환과 배정 변경·중간 저장·이어하기를 화면과 하네스에서 확인한다. 로드맵 2단계이며 침공형은 배양 후 방출 대기까지 다룬다.
기능 확장에 앞서 기존 조율 클래스의 책임을 분리하고 역할별 명명 규칙을 적용하여, 규칙 변경 위치와 명령·상태 변경 경로를 코드에서 추적할 수 있게 한다.

## 범위

- 포함: 기존 클래스의 책임·이름 점검, 단일 책임 Manager 구성, 역할별 클래스·파일·관련 참조 명명 규격화와 이관·회귀 검증. 새 생산 담당 Manager에도 같은 기준 적용.
- 포함: 배양액 1종, 재료 가공시설·공용 배양시설, 보급형·침공형 정의와 필요한 실행 상태. 기존 콘텐츠와 합쳐 자원 2종·시설 4종·생명체 3종을 다룬다.
- 포함: 기존 유기물 건설 흐름으로 두 시설 추가, 저장소를 통한 현재 회차 재료 공급·예약·소비, 가공 완료품의 전량 실제 입고와 반복 생산.
- 포함: 가공·배양의 20%/100% 전환·접근 불가/연구소 정지·상태 보존, 배양 대상 선택·반복·변경·출현과 보급형 합류·침공형 대기.
- 포함: 모델별 작업 자격, 보급형 배정·변경·해제, 담당 작업과 자동 건설·수집·운반의 연결, 기본/개별 작업 우선순위.
- 포함: 두 자원의 용량 합산·허용 목록·운반/재배치, 새 상태와 관계의 저장·복원·초기화, PC 가로 최소 화면과 공통 명령·검증 확장.
- 제외: 침공형 방출·외부 활동·전과 보고·멸망·결과의 실제 사이클(3단계), 세로 대응·Android 빌드/실기기·최종 성능 검증(4단계).
- 제외: 고급형·특화형, 시작 프로토타입의 추가 배양·모델 업그레이드, 배양 선택 해제/중지 버튼, 새로운 해금·강제 배양 순서·콘텐츠 제한·정식 아트 제작.

2026-10-28 사용자가 PLAN-009 실행을 승인했다. Manager 책임·명명 정비와 기존 기능 회귀 검증을 먼저 마친 뒤 가공·배양·보급형 운용을 구현한다.
후속 요청으로 Manager 책임 분리와 이미 구현된 클래스의 명명 정비를 이 PLAN의 실행 범위에 추가했다. 범위 추가는 PLAN 전체 실행 승인과 구분한다.
시작 상태는 계속 프로토타입 1개체·보급형/침공형 0개체·선배치 시설 없음이다. 추가 시설 건설 자원은 실제 수집으로 마련하며 무료 지급·선배치로 진입을 우회하지 않는다.

## Manager 책임과 명명 정비

한 Manager는 같은 이유로 변경되는 한 영역의 규칙 또는 조율을 맡는다. 같은 상태를 여러 Manager가 원본으로 보관하지 않으며, 명칭 변경과 함께 실제 책임·호출 경계를 확인한다.

| 기존 클래스 / 추가 영역 | 정비할 이름의 기준안 | 담당 책임 |
| --- | --- | --- |
| `SessionController` | `GameFlowManager` | 한 판의 준비·단계 전환·정지·재시작과 저장 시점 조정. 실제 직렬화·파일 저장은 Persistence에 위임 |
| `LaboratorySimulation` | `LaboratoryManager` | 연구소 시스템의 연결·실행 순서·갱신 조율. 건설 후보·우선순위·저장 허용 같은 개별 규칙은 담당 기능으로 분리하거나 위임 |
| `WorkerSystem` | `WorkerManager` | 개체의 작업 선택·전환·행동 수행. 시설 생산 진행도를 독자적으로 중복 갱신하지 않음 |
| `LogisticsSystem` | `LogisticsManager` | 공급처/목적지 선택·운반 수량·예약·수령/입고·운반 예외 |
| 가공·배양 생산 담당 추가 | `ProductionManager` | 시설 회차의 시작 조건·속도·진행·완료. 수집 회차와 공유할 경계도 함께 검토 |

위 이름으로 책임·명명 정비를 적용했고 ConstructionManager·ProductionManager를 구성했다. 최종 이관·유지 예외는 [TECH-006](../decisions/TECH-006-production-and-manager-boundaries.md)에 기록했다. 한 줄짜리 전달 클래스나 역할이 겹치는 Manager를 늘리지 않는다.
시설 진행·소비·완료품 대기, 개체 배정·Job은 기존 Thing 컴포넌트에 원본을 유지한다. Manager는 담당 기능을 통해 이를 갱신하며 예약 등 여러 개체에 걸친 상태는 해당 시스템이 관리한다.
Manager는 세션에 속하는 일반 C# 객체로 구성하고 필요한 의존성을 명시적으로 전달한다. Unity의 Update·입력은 기존 화면/실행 연결 경계를 통과하며, 화면과 하네스가 같은 조율 경로를 사용한다.

### 역할별 이름 기준

영문 표기·역할별 접미사·Manager·파일명 기준은 [명명 규칙](../agents/naming.md)을 적용한다. 이 PLAN은 실제 변경 대상·이관 표·검증 결과를 관리한다.
기존 `LogisticsStateValidation.cs`는 `LogisticsManager.Validation.cs`로 본체와 함께 이관했다. 관련 API·테스트·Editor 도구의 타입 참조도 갱신했다.
변경 전/후 이름·경로·책임과 유지하는 예외를 이관 표로 남기고, 선택 이유·담당 상태·명령/갱신 경로는 기술 결정에서 연결한다.

### 안전한 이관과 추적

- 먼저 기존 동작을 유지하는 이름·책임 정비를 검증한 뒤 생산 기능을 추가한다. 이름 변경 과정에서 공급 우선순위·작업 전환·시간·자원 규칙을 함께 바꾸지 않는다.
- 클래스와 파일을 바꿀 때 `.meta`·GUID, 씬/SO/프리팹의 스크립트 참조, 어셈블리·namespace 경계, 테스트 탐색과 문자열 참조를 점검한다. 필요한 호환 처리와 실제 로드 결과를 남긴다.
- 명명 정비만으로 정의 ID·Thing ID·생성 순서·저장 버전/runtimeKind·필드·enum 값 계약을 바꾸지 않는다. 새 생산 상태 때문에 필요한 저장 확장과 기존 클래스 이름 변경의 영향을 분리해 검증한다.
- 현재 사용하는 코드·문서의 참조는 새 이름으로 연결한다. 과거 검증 로그·소스 해시·결과 파일은 당시 증거로 보존하고, 이전 이름은 이관 표에서 찾을 수 있게 한다.
- 주요 명령·Job/생산 단계·예약 변경을 담당 코드와 관련 Thing ID·변경 이유로 추적할 수 있게 한다. 기존 상태 조회와 필요한 최소 진단 기록으로 검증하며 별도 대시보드·범용 로깅 프레임워크까지 확대하지 않는다.

## 구현 순서와 주요 경계

0. **책임·명명 기반 정비:** 기존 클래스의 역할과 호출 관계를 점검하고 이관 표·명명 기준을 작성한다. Manager 책임 분리와 이름/참조 정비 후 기존 초기 건설·물류·저장·실제 씬의 회귀 검증을 통과한 뒤 기능 확장을 진행한다.
1. **정의와 실행 상태:** 승인된 두 자원·네 시설·세 생명체에 필요한 최소 정의와 자격을 구성한다. 건설 재료, 생산 투입, 자원 결과물, 생명체 결과물을 구분하고 새 시설도 실제 자원·건설 작업 후 사용한다.
2. **두 자원 물류:** 저장 허용 목록과 운반 후보를 자원별로 확장한다. 저장소에서 생산시설로 현재 회차의 부족분만 공급하고, 완료품은 저장소에 먼저 실제 입고한다. 생산시설끼리 직접 전달하는 지름길을 추가하지 않는다.
3. **가공 회차:** 유기물 5개가 도착하고 시작 조건을 만족하면 한 번 소비해 배양액 1개를 생산한다. 기준 작업량 10초, 실제 작업자가 없으면 20%로 진행한다. 전량 실제 입고 전에는 다음 회차 준비·생산을 하지 않는다.
4. **배양 회차:** 새 시설은 선택 없음이며 공급·배양하지 않는다. 보급형/침공형 선택 후 배양액 2개를 한 번 소비하고 기준 작업량 20초에 1개체를 만든다. 현재 선택과 시작한 회차 대상을 분리하여 선택 변경은 다음 회차에 적용한다.
5. **보급형 운용:** 보급형만 가공/배양시설 한 곳에 직접 배정한다. 배정된 개체가 고정 상호작용 위치에서 실제 작업할 때 100%, 이동·다른 작업·미배정이면 조건에 따라 20%다. 20%와 100%를 합산하지 않는다.
6. **표시·저장·통합:** 기능 추가와 함께 공통 명령·상태 조회·저장·검증을 확장한다. 실제 초기 상태부터 저속 생산으로 첫 보급형을 배양하고, 배정에 따른 개선과 침공형 배양·대기까지 PC 최소 화면에서 연결한다.

물류는 기존 공급처 우선·경로 거리·최초 생성 순서·정상 운반 유지·집기 전/후 예외를 적용한다. 생산시설 목적지의 수용량은 이미 도착한 재료와 유효 입고 예약을 뺀 현재 회차 부족분이다. 배정 해제만으로 공급·기존 예약·도착 재료를 제거하지 않는다.
가공·배양은 재료가 모두 도착하고 조건을 만족하면 실제 작업자를 기다리지 않고 시작한다. 접근 불가·연구소 일시정지 때는 20%도 멈추며, 회복·시설 이동·작업자 변경 후 진행도와 소비 상태를 보존한다. 획득시설에는 무인 생산을 적용하지 않는다.
배양 완료 개체는 고정 상호작용 위치에 겹쳐 출현할 수 있다. 보급형은 미배정으로 자동 작업에 합류하고 침공형은 Map에 남아 방출 대기한다. 출현 후 다음 한 회차를 준비하며 개체의 이동·방출이나 저장소 입고를 기다리지 않는다.

### 배정 전환에서 구분할 두 경우

| 원인 | 현재 행동과 전환 |
| --- | --- |
| 플레이어가 배정 변경·해제 | 설정은 즉시 반영. 수집·가공·배양 작업은 해당 개체만 중단하고 시설 상태 보존. 정상 운반은 집기 전 이동부터 완료까지 유지. 그 밖의 이동·대기는 다시 선택 |
| 기존 배정을 유지한 채 담당 작업이 가능해짐 | 기존 우선순위의 후보에 포함. 정상 운반은 완료 후, 실제 수집은 현재 회차 자원 생성 후, 운반 외 이동·대기는 즉시 재선택. 무조건 담당 작업으로 강제 전환하지 않음 |

담당 시설의 재료 부족·대상 미선택·완료품 입고 대기·접근 불가 때 배정을 유지하며 가능한 자동 작업을 하고, 없으면 대기한다. 이미 시작한 회차는 재료가 소비되어 없어도 작업 가능한 진행 상태로 판단해야 한다.

## 구현 때 결정할 상세

- 신규 시설 비용·크기·상호작용 위치·건설 시간, 보급형 이동/운반 값·생산 작업 우선순위 기본값·동시 작업 인원은 D-059 안에서 결정한다. 새 게임 규칙이나 별도 사전 승인 목록으로 늘리지 않는다.
- 실제 작업 여부·접근 가능 판정과 시설/개체 갱신 순서를 공통 Map·Job·진행 제어에 연결한다. 같은 시간에 20%와 100%가 중복 적용되거나 개체 수만큼 생산 시간이 중복 진행되지 않도록 검증한다.
- 생산 회차·배정 관계·자원 종류별 예약의 상태 소유와 자료구조, 출력 입고 통지·출현 처리는 구현에서 정한다. 범용 레시피 편집기·전체 작업 프레임워크를 선행 조건으로 만들지 않는다.
- 기존 실제 플레이 v2와 진단 v1 저장의 호환/이행 또는 명시적 거부 방침을 정하고 검증한다. 손상·미지원 저장을 자동 초기화해 덮어쓰지 않고, 후보 전체 검증과 실패 시 정상 파일 보존을 유지한다.
- 여러 자원을 가진 같은 공급처의 동률 등 위임된 선택 순서는 최소한으로 정해 기록한다. 자원 종류보다 운반 가능한 공급처의 거리·생성 순서 규칙을 먼저 적용한다.

중요한 상태·저장 계약 선택은 [TECH-006](../decisions/TECH-006-production-and-manager-boundaries.md)에 기록했다. 위임 범위를 넘는 규칙 공백·충돌이 발견되면 해당 항목을 분리하여 사용자와 논의한다.

공통 게임 갱신으로 시간을 진행하며 무료 자원·즉시 건설·강제 개체 생성으로 실제 진입 검증을 대신하지 않는다. 복수 개체·희귀 예외의 격리 준비 상태는 실제 신규 시작과 구분한다.
생산 속도는 같은 작업 조건의 진행량으로 비교하며 이동·공급·입고 대기를 기준 작업시간에 포함하지 않는다. 검증용 시간 가속도 같은 규칙·정지 경로를 사용한다.
새 결과·명령·환경·실패/재검증 기록은 [실행 증거](evidence/PLAN-009/README.md)에 남겼다. 테스트 저장은 실제 플레이 슬롯과 격리하고, PC 검증을 Android·전체 게임 완료로 표현하지 않는다.

작업 종료 시 신규·교체 Sprite가 필요하면 `UnityProject/Assets/Sprites/Require/PLAN-009/README.md`에 명세를 작성해 이 PLAN에서 연결한다. 현재 계획 단계에서는 요청 파일/규격을 미리 만들지 않는다.
`development`이므로 정식 아트 미수령·사용자 시각 검수 대기는 완료를 막지 않는다. 필요한 기능·필수 검증은 충족해야 하며 아트 요청·수령·적용은 별도 흐름으로 관리한다.
