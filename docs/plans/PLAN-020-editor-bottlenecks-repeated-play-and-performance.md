# PLAN-020 Editor 런타임 운영 병목·반복 플레이·성능 검증

## 목표

현재 프로토타입을 Editor에서 반복 플레이하여 운영 병목을 실제 조작으로 해결할 수 있는지, 한 판·씬·팝업의 수명이 반복되어도 상태가 유지되는지 확인한다. 기존 구현을 대상으로 CPU·메모리·GC를 측정하고 재현 가능한 비교 자료와 문제·개선 후보를 남긴다. 이번 PLAN은 검증·진단 작업이며 제품 구현 수정이나 최적화를 수행하지 않는다.

이 PLAN의 완료는 Editor 범위의 완료다. 최신 버전의 Android 검증과 로드맵 4단계·D-070 전체 완료 판정은 후속으로 남긴다.

## 범위

- 포함: 생산·물류·저장·배정의 대표 운영 병목, 전체 사이클 반복, 저장·복원, 씬 전환·언어·Popup 연계, Editor 성능 측정, 기존 회귀 실행과 결함·최적화 후보의 재현·분석·기록.
- 제외: 제품 코드·게임 규칙·UI 동작·밸런스·에셋 구성의 변경, 발견한 결함 수정과 최적화 구현. 플레이어가 기존 기능으로 배치·배정·저장 설정을 조정하는 운영 개선 검증은 포함한다.
- 제외: APK/AAB·PC Player 생성, Player 스크립트 컴파일·IL2CPP·Addressables 콘텐츠 빌드 등 모든 빌드 테스트, 설치·ADB·실기기 검증, 모바일 성능 최종 판정.
- 제외: 새 콘텐츠·게임 규칙, 동시 개체 수 제한 도입, 엔진·렌더 파이프라인·패키지 교체, Google Sheets 연결, 정식 아트 교체와 광범위한 구조 재설계.
- 기존 임의(Temp) 에셋을 사용한다. 신규 Sprite 요청은 없으며 요청 폴더를 만들지 않는다.
- 작업 요청 근거: 2026-11-03 사용자 요청. Editor 런타임에서 운영 병목·반복 플레이·성능을 검증하는 PLAN 작성이며 빌드·실기기는 명시적으로 제외했다. 2026-11-03 사용자 실행 승인을 받았다.
- 검토 반영 근거: 같은 날 사용자가 두 보완 사항 반영을 요청하고, 밸런싱 전이므로 검증에 필요한 침공 처리의 상세를 위임했다. 검증용 침공 설정·표본 구성은 아래 기준으로 결정하며, 이는 제품 밸런스 확정이나 PLAN 실행 승인이 아니다. 사용자의 명시적 요청에 따라 이번에는 문서만 수정한다.
- 범위 재정의 근거: 같은 날 사용자가 성능 검증에 집중하고 구현된 범위를 변경하지 않으며, 실행 중 의견을 묻지 않고 검증 완료·기록 후 설명하도록 요청했다. 기존의 결함 수정·최적화 실행 항목은 진단·후속 후보 기록으로 대체한다. 이 문서 수정 요청은 실행 승인으로 간주하지 않는다.

## 사용자 의견과 발견 사항 처리

- 실행 승인을 받은 뒤에는 사용자 의견·선호·추가 결정이 필요한 사항을 중간에 질문하지 않는다. 기존 동작을 유지한 채 나머지 검증을 계속하고, 검증 작업과 기록을 마친 뒤 최종 보고에서 한꺼번에 설명한다.
- 검증 상세·대표 부하·계측 방식·격리된 침공 설정은 위임 범위에서 판단하고 근거를 기록한다. 규칙·UI·밸런스·구조 변경이 필요한 발견은 임의로 결정하거나 구현하지 않고 후속 검토 항목으로 남긴다.
- 발견마다 재현 조건·기대/실제 결과·증거·영향·원인 확실성·개선 선택지와 추천안을 기록한다. 사용자 판단이 필요한 이유를 표시하되 이번 PLAN의 답변 대기 조건으로 두지 않는다.
- 결함이 시나리오를 막으면 실패 지점과 영향을 보존하고 독립된 사례는 격리된 시작 상태에서 계속 검증한다. 준비 상태 주입을 실제 전체 사이클 성공으로 계산하지 않는다. 도구 문제는 범위 내 대체 계측으로 대응하고, 끝내 확인하지 못한 항목은 미검증·원인·후속 재개 조건으로 보고한다.

## 실행 설계

### 1. 기준 상태와 관찰 준비

- 실행 승인 후 코드 식별 정보·Unity/패키지 버전·PC CPU/GPU/RAM·해상도·품질·VSync/프레임 제한·포커스·Domain/Scene Reload·Profiler 설정을 기록한다.
- 테스트 슬롯·설정 경로를 격리한다. 직접 플레이가 사용자 저장·언어·표시 설정을 사용하는 경우 기존 파일의 존재 여부와 내용을 백업하고 종료·실패 시 복원한다. Editor 설정·열린 씬·Game View·백그라운드 실행 옵션도 원복한다.
- 기존 Edit/Play 테스트와 하네스를 재사용한다. 부족한 시나리오·관찰 수치만 추가하고 게임 규칙의 별도 시뮬레이터나 범용 성능 프레임워크는 만들지 않는다.
- 필요한 보조 코드·계측은 Editor/테스트 경계에 한정한다. 제품 코드를 수정해야만 가능한 관찰은 기존 Profiler·상태 조회 등 대체 수단을 우선 사용하고 한계를 기록한다. 테스트를 고쳐 제품 결함을 통과로 숨기지 않는다.
- 각 시나리오에 초기 상태·조작·실제 진행량·관찰 시간 한계·기대 상태를 둔다. 기능 테스트의 시간 가속과 실제 프레임 성능 측정을 분리한다.

### 2. 운영 병목의 발견과 개선

| 시나리오 | 플레이어의 개선 행동 | 확인할 결과 |
| --- | --- | --- |
| 생산 재료 부족·공급 지연 | 공급 시설·저장 설정·운반 작업을 조정 | 대기 이유가 실제 원인과 맞고 재료 도착 뒤 생산이 재개됨 |
| 저장 공간 부족·허용 자원 제외 | 공간 확보·저장소 추가·허용 자원 변경 | 운반·입고가 회복되고 전량 입고 전 다음 생산 회차가 잘못 시작되지 않음 |
| 긴 운반 동선·접근 불가 | 시설/저장소 이동 또는 막는 배치 해소 | 유효 경로로 회복되며 운반 소요 시간 또는 동일 시간 입고량이 개선됨 |
| 생산 배정과 물류 인력의 경합 | 보급형 배정·해제와 작업 허용 조정 | 20%/100% 생산 조건을 지키며 생산 속도와 운반 대기의 변화를 설명할 수 있음 |

- 각 사례를 같은 시작 스냅샷과 같은 게임 시간 구간으로 비교한다. 가능한 한 개선 변수 하나만 바꾸고 입고량·완료 회차·대기 시간 등 해당 사례의 지표를 기록한다.
- 최소 한 사례는 실제 Gameplay 화면의 상태 표식·선택 패널로 원인을 확인하고 UI 입력으로 개선까지 수행한다. 나머지도 공통 명령과 실제 상태 조회를 사용한다. 준비용 상태 주입은 사용자 조작 검증과 구분한다.
- 개선 전후 자원 소유·예약·운반 중 재료·배정 관계를 확인한다. 병목 상태 저장·복원 뒤에도 관계가 유지되고 같은 해결 행동으로 회복되는 사례를 포함한다.
- 숨은 상태 조작이나 대기 이유를 무조건 정상으로 바꾸는 수정으로 통과시키지 않는다. 기존 기능으로 회복하지 못하거나 표시·갱신 결함이 드러나면 실패 증거와 후속 개선 후보를 기록하며 제품 구현은 수정하지 않는다.

### 3. 전체 사이클과 수명 반복

- 공통 게임 경로로 초기 건설 → 생산·운반 → 보급형/침공형 배양 → 방출·보고 → 멸망 → 결과 → 새 판을 최소 3판 연속 확인한다. 진행 한계를 두고 타임아웃은 실패로 기록한다.
- 그중 최소 1판은 Test Runner와 별개의 실제 Editor Play에서 화면 입력과 렌더링을 확인한다. 시간 가속 사용 여부·구간을 명시하며 결과 화면으로 상태를 직접 바꾸는 것을 한 판 완료로 세지 않는다.
- 반복 중 Title 복귀·이어하기, 생산/운반 중 저장·복원, 결과 단계 이어하기, 새 게임 덮어쓰기 확인/취소를 포함한다. 종료 중 진행 없음, 자원·외부 침공 성과의 중복 누적 없음, 새 판의 이전 개체·예약·보고 정리를 확인한다.
- 가로·세로 Game View와 ko/en을 포함한다. 설정·Confirm·Notice를 열고 언어 변경·크기 변경·멸망 경계를 통과해 텍스트 갱신·팝업 정리·입력 잠금 해제를 관찰한다. Editor의 해상도/포커스 변경은 실제 회전·앱 생명주기 검증과 구분한다.
- 저장 실패·복원 실패·확인 후 포커스 상실/복귀는 기존 회귀를 재사용하여 현재 상태 보존·재시도·콜백 1회 전달을 확인한다.
- Bootstrap 정상 진입, Title/Laboratory 직접 진입, Domain Reload ON/OFF, 양 Reload OFF의 반복 Play를 기존 검증 경로로 확인한다. 핵심 반복 진입은 각 설정에서 최소 2회 수행한다.
- 매 판/씬 전환 후 SceneFlowManager·GameDataStore·EventSystem·PopupHost의 기대 개수, 종료된 세션·View·Popup·구독의 잔존 여부와 입력 가능 상태를 확인한다. 앱 수명 객체의 정상 재사용과 누수를 구분한다.

### 4. 성능 기준 측정과 개선 후보 분석

- 정상 초기 운영·중간 운영·고부하 운영의 3개 재현 상태를 고정한다. 고부하는 현재 맵·정의·자원 규칙 안의 시설·생명체·운반·외부 침공/보고 증가로 구성하며 실제 수량·준비 방법을 기록한다. 새 개체 수 상한을 게임 규칙으로 도입하지 않는다.
- 기능 시나리오의 가속 시간과 달리 성능은 실제 렌더링·정상 시간 배율에서 측정한다. 각 상태는 초기 준비 후 최소 30초 워밍업, 60초 관찰을 3회 수행한다. 초기 로딩·첫 언어 전환·저장·씬 전환 비용은 정상 운영 표본과 분리해 기록한다.
- 검토 보완 1 — 연구소 운영 부하와 침공·보고 부하를 분리해 측정한다. 밸런싱 전인 현재 침공 수치를 성능 검증의 고정 제약으로 취급하지 않는다. 조기 멸망으로 관찰 시간이 부족하면 격리한 검증용 설정에서 목표 점수를 늘려 유효 관찰 시간을 확보할 수 있다. 활동 주기·성과 계산·보고 단계/보관 한도는 가능한 한 유지하며 실제 적용값·변경 이유·측정 대상 보고 단계를 기록한다.
- 검증용 설정은 별도 인스턴스와 테스트 저장 경로에만 적용하고 제품 JSON·공유 Data·사용자 저장을 변경하지 않는다. 부하·표시 조건 비교에는 같은 기준 설정·시작 상태를 사용하고 비교 변수만 바꾼다. 활동·성과 누적 또는 목표 도달에 따른 정상 종료 로직을 비활성화하지 않는다. 전체 사이클 검증은 제품 설정에서 별도로 수행해 성능용 설정이 종료 검증을 대체하지 않게 한다.
- 각 성능 표본에 진행 단계·활동 개체 수·실제 게임 진행 시간을 남긴다. 예상하지 못한 멸망·결과 화면·포커스 정지·메뉴 전환이 섞인 표본은 운영 성능으로 합산하지 않고 원인을 기록한 뒤 조건을 바로잡아 재측정한다. 정상 전환 비용은 별도 지표로 보존한다.
- 검토 보완 2 — 같은 게임 상태에서 시설 상태 표시 ON/OFF, 아이콘↔설명 전환, 전체 보기의 다수 표식, 보고 목록 펼침/접힘을 비교한다. 보고 보관 한도에 도달한 뒤 스크롤 중 새 보고 추가·오래된 보고 제거, 큰 글씨·ko/en·가로/세로 전환에 따른 재배치도 포함한다. 모든 조합의 전수 검사가 아니라 각 조건을 포괄하는 대표 조합을 측정하고 조건별 CPU·GC·표시 객체 수를 남긴다.
- 현재 구현에서 숨긴 동안의 상태 변화가 다시 표시하는 첫 정상 갱신에 반영되는지 확인한다. 스크롤 위치 또는 제거된 행의 기존 대체 위치, 시설 선택, 표식 클릭, 언어/글씨 크기, 새 판 정리를 관찰한다. 보고 표시·열람·생략 여부와 무관하게 같은 활동의 성과가 정확히 한 번 누적되는지도 비교한다. 캐시·갱신 빈도·목록 재사용의 변경은 후보 제안만 남긴다.

- 예비 측정에서 비교 지표·허용 변동·문제 판정선을 정하고 본 측정 전에 수치와 근거를 고정한다. 같은 조건의 반복 편차를 반영하며 결과가 나쁘다는 이유로 판정선을 사후 완화하지 않는다. 모바일 FPS/메모리 합격선으로 사용하지 않는다.
- 재현 가능한 큰 비용·반복 할당·수명 누수가 확인되면 측정 근거·추정 원인·영향 범위를 분석한다. 캐시·갱신 빈도·목록 재사용 등의 개선 후보에는 예상 효과와 무효화·언어 전환·새 판 초기화 위험을 기록하되 구현하지 않는다.
- 부하·표시 조건별 차이와 반복 실행에 따른 추세를 비교한다. 최적화 전후 비교나 개선 효과를 실행한 것으로 보고하지 않는다. 문제가 발견되지 않으면 관찰 범위와 한계를 포함해 그 결과를 기록한다.
- 별도로 정상 배율의 최소 20분 연속 Editor 실행을 수행한다. 운영과 메뉴 왕복·팝업·언어 전환을 섞되 실제 운영 시간을 최소 15분 확보하고, 전환·결과·메뉴·일시정지 시간을 별도 기록한다. 필요하면 위의 격리된 침공 설정을 사용한다. 동일 상태로 돌아온 시점의 메모리·객체 수를 비교하며 자연스러운 보고/콘텐츠 증가, 최초 폰트/테이블 캐시 증가, 종료 객체 잔존을 구분한다. 강제 GC만으로 누수 해결을 판정하지 않는다.
