# PLAN-025 최신 버전 Android 통합 검증과 프로토타입 완료 판정

## 목표

PLAN-024까지 반영한 현재 구현의 전체 게임 사이클·병목 개선·저장 복원·모바일 동작을 같은 소스 기준으로 검증하고, 로드맵 4단계와 D-070의 네 완료 기준을 판정한다. 최근 추가한 씬 흐름·Localization·공용 Popup·약탈형·물마루 TMP·연출을 Android에서 함께 확인하는 것이 이 PLAN의 목적이다.

## 범위

- 포함할 기본 범위: 최신 소스의 정적 확인·Editor Edit/Play 통합 회귀, 최근 기능의 연결·저장 호환 검증, 실행 증거와 완료 기준 연결표 작성.
- 승인된 Android 범위: ARM64/IL2CPP 최종·진단 APK와 필요한 로컬 Addressables 콘텐츠 빌드, 연결된 SM-G977N의 오프라인 실행·양방향 터치·반복 플레이·성능 검증 및 D-070 최종 판정. 실행 범위와 필수 완료 조건에 포함한다.
- 검증에 필요한 최소 테스트·계측·빌드 진입점 보완과 재현 자료 작성은 포함한다. 아래 실행 설계에 따라 기존 도구의 Editor 의존성과 고정된 PLAN/빌드 옵션을 확인한다. 도구 보완도 실행 승인 후 진행하며 별도의 게임 규칙·범용 성능 프레임워크를 만들지 않는다.
- 제품 결함·성능 문제를 발견하면 원인·재현·영향·수정 후보를 기록한다. 제품 코드·밸런스·에셋 구성 수정은 이번 검증 범위에 자동 포함하지 않으며, 필요한 수정 범위를 정한 뒤 별도 승인 절차를 따른다.
- 제외: 신규 콘텐츠·규칙, 최종 밸런싱, 정식 아트 교체, Google Sheets 연결, 아래 승인한 Feel 복원 외 엔진·패키지 교체, iOS·스토어 배포·출시 서명 설정, 광범위한 구조 변경.
- 환경 복원 예외: 2026-11-06 사용자가 “Feel 6.3 사용과 호환성 검증 승인”을 명시했다. 이후 My Assets 다운로드가 실제로 제공한 패키지는 기존과 같은 Feel 5.9.1이었다. 기존 버전 복원으로 진행하며, 6.3 승인 기록을 실제 사용·검증 결과로 대신하지 않는다. 기존 DOTween Pro·Text Animator와 함께 현재 참조·효과음·피드백 호환성을 검증한다.
- 기존 임의(Temp) 에셋으로 기능을 검증한다. 신규 Sprite 요청은 없다. [PLAN-014의 16종 요청](../../UnityProject/Assets/Sprites/Require/PLAN-014/README.md)은 지정된 별도 art PLAN과 사용자 시각 확인 절차를 유지하며 이 PLAN의 실행 선행 조건으로 삼지 않는다.
- 작업 요청 근거: 2026-11-06 사용자가 추천한 내용으로 PLAN-025 작성과 문서 불일치 수정을 요청하고, 실행하지 않은 `proposed` 상태 유지를 명시했다.
- 검토 보완 근거: 같은 날 사용자가 모바일 계측 경로, APK 빌드 조건, Android 입력·앱 수명 경계, 남은 문서 불일치의 네 보완 사항을 문서에 반영하도록 요청했다. 실행 승인은 포함하지 않는다.

## 승인 조건

- 2026-11-06 사용자가 “PLAN-025를 active로 전환하고 실행해줘. 휴대폰은 데스크탑에 연결해둘게”라고 요청했다. PLAN 활성화·Editor 회귀·연결 기기 검증 준비를 승인받았으며 유일한 `active`로 전환했다.
- [빌드 실행 조건](../agents/verification.md#build-test-authorization)에 따라 별도 확인했고, 2026-11-06 사용자가 “APK·콘텐츠 빌드 및 연결 기기 검증 승인”이라고 명시했다. 최종·진단 ARM64/IL2CPP APK와 로컬 Addressables 빌드, 연결 기기 설치·오프라인·저장 복원·성능 검증을 승인받았다. 같은 범위의 빌드는 재승인을 요구하지 않는다.
- 종합 목표를 유지하며 아래 Android 실행 설계와 완료 기준을 적용한다. 발견된 회귀 실패를 먼저 처리하고 빌드하며, 제품 결함 수정은 위 범위 규칙에 따라 별도로 판단한다.

## 실행 설계

### 1. 기준 상태와 검증 환경

- 실행 시점의 커밋·작업 트리 차이·Unity/패키지 버전·빌드 씬·기기 모델/OS·화면 크기·품질·프레임 제한을 기록한다. 문서 작성 시점의 HEAD는 `8db7bc0`이며 실제 검증 기준은 실행 때 다시 고정한다.
- Unity 6000.3.27f1 프로젝트와 기존 Editor 세션·CLI 연결을 확인하고 실제 지원 명령을 사용한다. 같은 프로젝트에 충돌하는 Editor를 중복 실행하지 않는다.
- Editor와 기기의 기존 저장·설정 파일 존재 여부와 내용을 보존한다. 테스트 슬롯을 격리하고 기기에서 격리가 불가능하면 복구 가능한 백업을 확보한 뒤 검증한다. 백업 전 초기화·앱 데이터 삭제·재설치로 사용자 데이터를 잃지 않게 한다.
- 종료·실패 시 저장·언어·화면/회전·네트워크·Editor 설정을 복원하고 대조한다. 설치 앱의 버전·남은 APK 등 복원하지 않은 항목은 별도로 기록한다.

### 2. 최신 Editor 통합 회귀

- 현재 코드의 전체 Edit/Play 회귀를 한 번 실행하고 테스트 탐색 수·통과·실패·건너뜀과 원본 결과를 보존한다. PLAN-023의 357/357·71/71, PLAN-024의 대상 33/33을 현재 테스트 수로 고정하지 않는다.
- Bootstrap → Title → Laboratory → Title, 새 게임·이어하기·재시작·저장 실패 복구를 확인한다. 기존 검사를 재사용해 직접 씬 진입과 Domain Reload ON/OFF 재진입도 확인한다.
- 약탈형의 배양·혼합 방출·입고 차단/회복, 대기 중 저장 복원·중복 지급 방지·멸망 경계·새 판 초기화를 기존 공통 명령과 실제 상태로 검증한다.
- 로딩 최소 표시 시간·입력 잠금·실패/재시도, ko/en·팝업·물마루 글리프, 방출 성공 시 피드백 1회와 지도 자동 이동의 수동 입력 중단을 최근 변경의 통합 확인 대상으로 삼는다.
- 실패를 보존하고 원인을 분류한다. 수정이나 새 실패가 없는 상태에서 같은 전체 회귀를 반복하지 않는다. 수정이 승인되어 반영되면 영향받은 검사와 통합 범위를 다시 확인한다.

### 3. Android 패키징과 오프라인 첫 실행 — 승인 후

- 기존 ARM64·IL2CPP 구성과 Gameplay 씬 목록을 확인한다. Diagnostics·템플릿 씬은 제품 APK에서 제외하고, 외부 연출 에셋·SO·폰트·번역 테이블·로컬 콘텐츠가 실제로 포함되는지 확인한다.
- 기존 [Android 빌드 도구](../../UnityProject/Assets/Scripts/Editor/Validation/LaboratoryPlayerBuild.cs)는 PLAN-013/014 진입점과 `BuildOptions.Development`가 고정되어 있다. 재사용 전에 PLAN 번호·빌드 종류·실행 ID를 명시하는 최소 진입점을 준비하고, 이전 PLAN의 산출물·증거를 덮어쓰지 않는지 확인한다.
- 최종 기능·체감 검증 APK는 Development·Script Debugging·Autoconnect Profiler를 끈다. 진단 APK는 Development를 켜고 필요한 Profiler 연결만 사용하며, Script Debugging·Deep Profiling의 사용 여부와 이유를 기록한다. 두 APK의 실제 빌드 옵션·코드 스트리핑·콘텐츠 설정 차이를 빌드 보고와 대조한다.
- 산출물은 `UnityProject/Builds/PLAN-025/`, 증거는 `docs/plans/evidence/PLAN-025/` 아래에서 빌드 종류·실행 ID별로 분리한다. 진단용 상태 주입·계측 진입점이 최종 APK에 남지 않는지도 확인한다.
- 승인된 APK와 필요한 Addressables 콘텐츠를 같은 기준 소스에서 생성한다. 로그·오류/경고·산출물 경로·크기·SHA-256·패키지 식별 정보를 남기고 설치한 APK가 해당 결과와 같은지 대조한다.
- 검증용 새 데이터 상태에서 네트워크를 끈 최초 실행으로 JSON·Localization·물마루 Dynamic TMP·팝업·로딩·음원/연출을 확인한다. Editor 캐시나 과거 다운로드가 성공 조건을 대신하지 않게 한다.
- 기존 저장을 가진 업그레이드/이어하기 경로는 새 데이터 첫 실행과 구분한다. 지원하는 저장 버전의 복원, 손상·비호환 오류 표시와 기존 저장 보존을 확인하며 임의 해시 허용으로 통과시키지 않는다.

### 4. 실기기 전체 사이클·병목·수명 — 승인 후

- 실제 기기 한 종류에서 제품 수치·정상 시간 배율로 초기 건설부터 멸망·결과·다시 시작까지 최소 2판 연속 수행한다. 최소 한 판은 가로, 한 판은 세로를 중심으로 진행하고 일반 침공형과 약탈형을 포함한다.
- 실제 터치로 시설 선택·이동/회전·배정·저장 설정·배양·방출·보고를 조작한다. 조작 중 방향 전환, 핀치·드래그, 큰 글씨·ko/en, 열린 팝업과 로딩 중 앱 복귀를 대표 조합으로 확인한다.
- Android의 실제 뒤로가기를 로딩/전환·중첩 팝업·기존 화면에서 각각 확인한다. [PLAN-019의 입력 우선순위](PLAN-019-shared-popup-system.md)에 따라 한 입력은 한 번만 처리하고, 최상위 팝업과 뒤 화면이 동시에 닫히거나 닫을 수 없는 팝업 뒤로 입력이 전달되지 않아야 한다.
- 팝업 확인 후 닫기 애니메이션 중 백그라운드 전환 → 복귀를 확인한다. 유효한 확인 의도는 한 번만 전달하고, 대기 중 소유 범위가 종료된 의도는 실행하지 않는다. 반복 복귀 후 콜백 중복·입력 잠금 잔존·오래된 터치의 전달이 없어야 한다.
- 홈 이동 후 복귀와 화면 잠금/해제는 별도 사례로 기록한다. 로딩·팝업·조작 중 대표 상태에서 전경/배경 전환과 진행 정지·입력 복구를 확인하며, Editor의 Pause/Focus 메시지 주입을 실기기 증거로 대신하지 않는다.
- 재료/공급 대기, 저장 공간·허용 자원, 접근 불가·긴 동선, 생산 배정과 물류 인력 경합을 기존 PLAN-020 사례와 연결한다. 기기에서 최소 한 사례는 표시된 대기 이유를 보고 실제 UI로 해결하고 동일 게임 시간의 입고량·회차·대기 시간 등으로 전후를 비교한다.
- 생산·운반·보급품 대기 중 저장·앱 종료·재실행, 결과 화면 이어하기·새 판을 검증한다. 종료/백그라운드 구간의 생산·침공 추가 진행, 자원·예약·회차 중복 반영, 이전 판 상태 잔존이 없어야 한다.
- 실제 프로세스 종료는 복구 가능한 검증 데이터에서 마지막 자동 저장 성공을 확인한 뒤 강제 종료하고 프로세스 부재를 확인하는 사례로 분리한다. 종료 전 마지막 성공 저장의 해시·게임 시간·회차·재고·예약과 재실행 후 상태를 대조하고, 종료 중 경과 시간과 재실행 후 진행을 구분한다. 아직 저장하지 않은 메모리 상태를 복원 기준으로 삼지 않는다.
- 특수 상태 주입·시간 가속은 별도 경계 검사로 표시한다. 준비 상태나 자동 명령만으로 실제 터치·전체 사이클 완료를 판정하지 않는다.

### 5. 모바일 반복 운영·성능 — 승인 후

- 기존 [PLAN-020 계측 도구](../../UnityProject/Assets/Scripts/Editor/Validation/Plan020Probe.cs)는 `EditorApplication.update`·Editor 테스트 슬롯·PLAN-020 증거 경로에 의존한다. Android 계측에 그대로 사용하지 않고, 본 측정 전에 기기에서 상태 준비 → 수집 → 원시 결과 추출이 가능한지 짧은 예비 실행으로 확인한다.
- 최종 APK는 기기에서 지원하는 OS 프레임 추적·메모리 조회·화면 기록을 우선 사용한다. 진단 APK는 필요할 때만 최소 Player 계측을 추가하되 Editor 참조를 포함하지 않는다. 지표별 수집 방법·실제 명령/도구 버전·단위·표본 시각·유효성·추출 경로와 최종/진단 APK에서의 측정 가능 여부를 표로 고정한다.
- 프레임 원시 표본과 집계 조건을 함께 보존하고, 입력 지연은 입력 발생부터 화면 반영까지의 기준과 측정 해상도를 명시한다. GC·메모리는 사용한 카운터의 의미와 유효성을 확인한다. 미지원·누락 표본을 0으로 처리하거나 Main Thread 시간·평균 FPS를 렌더 프레임 시간으로 대신하지 않는다.
- 초기·중간·고부하의 재현 가능한 상태를 고정한다. PLAN-021의 시설 8개·작업자 24명·외부 침공형 16명 상태를 출발점으로 재사용 가능 여부를 확인하고 약탈형·현재 UI를 포함한 실제 수량과 준비 방법을 기록한다. 새 개체 수 상한을 도입하지 않는다.
- 준비 저장의 버전·DataHash·파일 해시·수량과 기기로 전달/복원하는 방법을 기록한다. 각 APK의 파일 접근 가능 여부를 먼저 확인하고, 최종 APK에서 직접 주입이 불가능하면 공통 UI로 같은 상태를 재현하거나 보존된 검증 저장을 이용한다. 상태 준비 성공과 실제 터치 검증 결과는 분리하고 사용자 저장 백업·복원 조건을 유지한다.
- 상태별 30초 예열 후 60초를 3회 측정한다. 실제 렌더링·정상 배율에서 프레임 시간 중앙값/p95/최댓값·입력 반영 지연·GC·메모리·관찰 가능한 발열 상태를 기록한다. 초기 로딩·언어 전환·저장 비용과 정상 운영을 구분한다.
- 기기·계측 조건을 확인한 예비 측정 뒤 본 측정 전에 허용 프레임 시간·입력 지연·메모리 추세의 수치 기준과 이유를 고정한다. Editor 수치를 모바일 합격선으로 쓰거나 결과에 맞춰 사후 완화하지 않는다. 계측 불가능한 값은 미측정으로 남긴다.
- 고부하에서 상태 표식 ON/OFF·보고 목록·언어/방향 전환의 대표 조합을 비교하고, 정상 배율로 최소 20분 연속 관찰한다. 그중 실제 운영을 15분 이상 확보해 저장·메뉴 왕복·입력 반응과 동일 상태 복귀 시 메모리·객체 잔존 추세를 확인한다.
- 조기 멸망으로 표본이 끊기면 검증 전용 설정·슬롯에서 목표값만 조정할 수 있다. 제품 JSON·공유 Data·사용자 저장을 보존하고 차이와 게임 진행량을 기록한다. 제품 수치의 2판 완료 결과와 분리한다.
- 위 빌드 조건에 따라 최종 APK와 진단 APK를 같은 소스로 구분하고 계측·로그 오버헤드를 기록한다. 원시 표본은 APK 해시·상태 해시·실행 ID와 연결해 PLAN-025 증거 경로로 추출한다. 필수 지표를 최종 APK에서 확인할 수 없으면 대체 방법과 판정 한계를 남기고 해당 항목은 미검증으로 유지한다.
