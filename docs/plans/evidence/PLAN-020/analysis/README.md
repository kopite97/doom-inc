# PLAN-020 측정 결과와 후속 후보

모든 수치는 Editor 결과다. 제품 구현·밸런스·아트를 변경하거나 코드 최적화 효과를 측정한 결과가 아니다.

## 반복 성능 표본

각 행은 같은 시작 저장 상태에서 30초 워밍업 + 60초 관찰이다. CPU는 Main Thread recorder의 중앙값/p95, GC는 프레임 할당량 중앙값이다. Editor 자체·계측 비용과 대기가 포함된다. 각 행의 JSON과 CSV는 이 디렉터리에 보존했다.

| 초기 | 1 | 24998 | 2.300 / 2.631 | 121.3 | 90.00 |
| 초기 | 2 | 25081 | 2.295 / 2.612 | 121.3 | 90.00 |

- 반복 편차는 사전 고정한 불안정 기준(p95 범위가 최솟값 대비 20%와 2ms를 모두 초과)에 해당하지 않았다. 고부하 지연은 일회성 이상치가 아니다. 고부하 최댓값은 703~731ms였다.
- 초기→중간, 중간→고부하 증가는 사전 CPU 조사 기준(20%와 2ms를 모두 초과)을 넘는다. 모든 상태의 GC 중앙값은 사전 반복 할당 조사 기준 64KiB/프레임을 넘었다.
- 표본 시작/종료 모두 Playing, 일시정지 아님, 종료·메뉴 전환 없음. 게임 시간도 실제로 진행됐다. 고부하의 끝 프레임 경계 때문에 워밍업 포함 진행 시간이 약 0.2~0.5초 짧지만, 멸망이나 포커스 정지가 섞인 표본이 아니다.
- 고부하의 시설/내부 작업자/외부 침공형은 8/24/16이다. 이 수량은 재현 조건이며 새 게임 규칙이나 허용 상한이 아니다.

분리 표본은 각각 30초+60초 1회다. 연구소만으로도 큰 지연이 재현되고 침공만인 조건은 초기 상태와 비슷했다. 표식을 꺼도 큰 지연이 유지되므로 표식 최적화만으로 이 고부하 문제를 해결할 수 있다는 근거는 없다. 조합별 언어·글씨·방향 비교는 각 조건을 포괄하는 대표 표본이며 세 변수 각각의 독립 효과를 추정하지 않는다.

보고는 제품 보관 한도 20개, 상세 전환 기준 60을 유지한다. 고부하 표본에서 초반 상세 단계가 빠르게 끝나므로 주 측정 구간은 요약 단계다. 상세→요약과 성과 1회 누적은 제품 설정 전체 사이클과 기존 회귀에서 별도로 검증했다.

## 호출 단위 진단

[별도 CPU 진단](../synchronous-costs.json)은 계측 루틴과 분리해 동기 호출을 20회 예열/120회 측정했다. 같은 프레임의 시간 비율이나 실제 FPS로 환산하지 않는다.

| 호출 | 초기 / 중간 / 고부하 중앙값 (ms) |
| --- | ---: |
| LaboratoryManager.Advance(0.016) | 0.012 / 1.532 / 38.680 |
| 모든 시설의 상태 조회 | 0.000 / 0.131 / 0.462 |
| 맵의 경로 1개 조회 | 0.046 / 0.085 / 0.177 |
| 상태 표식 갱신 ON | 0.001 / 0.204 / 0.584 |
| 화면 갱신, 패널 닫힘 | 0.043 / 0.045 / 0.048 |
| 화면 갱신, 보고 목록 | 0.092 / 0.109 / 0.659 |

고부하 표식 설명 열림/접힘의 중앙값은 0.605/0.580ms였다. 실제 표식 선택 처리로 설명 상태를 바꿨으며 별도 제품 UI 구현을 만들지 않았다. 설명 토글·선택·스크롤 보존의 합성 입력 회귀도 통과했다.

호출 단위 할당량은 **미계측**이다. `GC.GetAllocatedBytesForCurrentThread()`가 1MiB 배열 생성에도 0을 반환한 [교정 결과](../allocation-counter-calibration.json) 때문에 해당 진단 JSON의 `medianBytes/p95Bytes=0`은 무효다. 이를 무할당이라고 해석하지 않는다. GC 근거는 실제 프레임의 Unity ProfilerRecorder 표본이다. CLI 동기 호출은 요청 제한 30초를 초과했지만 Editor 평가가 끝나 결과 파일을 남겼다. 평가 완료 확인 후 장시간 관찰을 시작했으며 중복 실행하지 않았다.

## 발견과 후속 제안

### F1. 다수 작업자의 반복 작업 탐색 비용 — 우선순위 높음

- 재현: 고부하 fixture, 정상 배율, 약 30초 이후 운영. 3회 반복과 연구소 단독 표본에서 재현됐다. 예상은 개체 증가에도 조작 가능한 운영 유지이며 실제로 수백 ms 프레임 지연이 발생했다.
- 확인된 사실: 고부하의 순수 게임 갱신 동기 호출이 약 38.7ms로 UI 개별 갱신보다 크다. 시설 상태 OFF와 침공 제외만으로 문제는 해소되지 않는다.
- 원인 후보: `WorkerManager.SelectWork`가 유휴 작업자마다 탐색하며 `ReachableTargets`에서 모든 시설의 경로를 먼저 구한 뒤 작업 종류/가능 여부를 거른다. 물류도 후보별 거리 계산을 반복한다. `GridPathfinder.FindPath`는 호출마다 Dictionary·Queue·경로 목록을 만든다. `LaboratoryManager.Advance`는 긴 프레임을 최대 0.05초 단위로 나누므로, 비싼 탐색이 한 프레임 안에서 여러 번 반복되는 영향도 가능하다. 정확한 메서드별 할당 비율은 아직 확인하지 않았다.
- 추천: 작업 가능 후보를 먼저 걸러낸 후 경로 계산 → 같은 맵 상태의 거리/경로 또는 검색 버퍼 재사용 → 유휴 작업자 재탐색 시점 제어를 순서대로 검토한다. 동률 선택 순서, 시설 이동/회전, 막힘 해소, 예약/재료 변화, 저장 복원·새 판 때 무효화를 반드시 검증한다.
- 기대 효과는 중복 탐색·할당 감소이며 아직 구현/효과 측정을 하지 않았다. 개체 상한 추가나 밸런스 변경으로 측정 부하를 없애는 방안은 추천하지 않는다. 후속 최적화 PLAN 승인이 필요하다.

### F2. 운영 중 반복 할당과 UI 재계산 — 후속 계측 후보

- 초기 상태부터 Editor 전체 프레임 할당이 반복된다. 제품 UI·게임 로직·Editor 비용이 섞여 있으므로 전체를 제품 누수나 UI 할당으로 단정하지 않는다.
- 상태 표식은 설명을 숨겨도 상태 조회와 문구 포맷을 수행한다. 보고 목록과 동적 HUD는 반복 포맷한다. 반면 고정 문구는 이미 언어 변경 시에만 갱신하므로 같은 개선을 중복 제안하지 않는다.
- 추천: F1 이후 개별 경로의 Unity Profiler 할당 스택을 추가 확인하고, 표시 값/언어/글씨 크기/세션 세대가 바뀔 때 갱신하는 범위를 좁힌다. 값이 바뀐 뒤 재표시, 보고 추가·제거 중 읽기 위치, 언어 변경·새 판의 무효화 누락이 주요 위험이다. 이번 PLAN에서는 캐시를 추가하지 않았다.

### F3. Localization 가져오기 반복 검사의 Addressables hash 차이

- 전체 Edit 회귀의 1개 실패다. 번역 원본/표시 실패가 아니라 반복 가져오기 후 `.asset` 바이트 비교에서 발견됐다. [실행 결과](../edit-regression.json), [설정 diff](../addressables-hash-diff.txt).
- 원본 에셋을 복원·다시 임포트한 뒤 [대상 검사 1개만 재실행](../edit-localization-repeat.json)해 같은 위치와 같은 두 해시로 실패했다. Git diff는 `m_currentHash` 한 필드뿐이고 번역 테이블/CSV 내용 차이는 없었다. 해시가 변한 사실은 재현됐지만 어느 패키지 내부 갱신이 원인인지는 확정하지 않았다. 후속 작업은 등록 내용과 파생 해시의 갱신 시점을 분리해 확인하는 것이다. 원인 확정 전에 테스트를 완화하거나 무시하지 않는다.

## 20분 연속 실행

- [장시간 관찰 원본](../soak-final.json): 실제 1200.01초(20분), 메뉴·전환/진단 조작 대기를 보수적으로 제외한 운영 1057.69초(17분 37.69초), 게임 시간 1096.31초. 나머지 142.32초는 Title·팝업·언어 작업에서 진단 코루틴이 기다린 시간 등을 포함하며 전부 게임 일시정지였다는 뜻은 아니다. 시간 가속·직접 Advance를 사용하지 않았다.
- 처음에는 고부하와 동일한 시설 8·내부 작업자 24·외부 침공형 16이다. 정상 배양으로 개체가 증가했다. 반복 탐색이 심해져 9→10번 관찰 사이 실제 약 193초에 불과 3프레임만 진행됐다. 분 단위 표시는 예정된 관찰 번호다. 긴 프레임 발생 뒤 관찰이 몰린 경우 실제 간격은 `state.utc`를 사용한다. 외부 입력이 30초 내 응답하지 못한 기록도 보존했다.
- 두 번째 Title 복귀 후 실제 명령으로 기존 보급형 26명의 우선순위를 모두 0으로 변경해 **당시** 4명에게 작업을 남겼다. [조작 전후](../soak-worker-policy.json). 개체를 제거하지 않았고 새로 배양된 개체는 계속 추가된다. 이후 14→15번 구간은 약 60초에 4064프레임, 게임 진행 약 60초였다. 처음과 끝을 고정 부하 성능 비교로 합산하지 않는다. 이 관찰은 작업 탐색이 주원인이라는 가설을 지지하며, 개별 메서드의 정확한 비중을 증명하지 않는다.
- Title 왕복 2회에서 전환 전/이어하기 직후 게임 시간은 각각 298.38/298.38초, 668.3/668.3초였다. 두 Title의 GameObject 수는 77/77, Unity 사용 메모리 358.39/358.02MiB. 두 복귀 직후 객체 수 134/134. 후기 보고 화면은 17~19번 및 종료 시 모두 519개였다. 공용 flow/store/EventSystem/PopupHost는 각 1, 닫힌 팝업은 0, 종료 후 조작 가능, 저장 오류 없음. 정상 생산에 따른 Thing 51→65 증가와 화면 행 최초 생성을 누수로 계산하지 않는다.
- 시작/종료 Unity 사용 메모리 359.16→361.37MiB, 예약 메모리 동일. 같은 Title에서 지속 증가하지 않았고 사전 조사 기준을 넘지 않았다. 관찰 범위에서 수명 누적 징후가 없지만 모든 C# 참조·네이티브 누수가 없음을 증명하는 힙 스냅샷은 아니다.
- [시작 GC](../soak-gc-start.json)와 [종료 GC·품질](../soak-gc-end.json): 각 세대 카운터가 동일하게 1093→1613, 차이 520. 같은 수치를 세 번 합산하지 않는다. 강제 GC를 호출하지 않았다. 품질 Ultra·UniversalRP·Profiler/Deep Profile OFF·대상 Android의 **Editor Play**이며 Android Player를 실행한 결과가 아니다. 초반 1MiB 할당 카운터 교정 1회가 포함된다.

## 사용자 판단이 필요한 후속 사항

- 최적화 실행 시점과 범위: F1을 우선하되 이번 작업에서는 수정하지 않는다.
- 정식 아트가 들어간 뒤 목표 동시 작업자/시설 규모와 Android 기기별 프레임·메모리 예산을 정할 필요가 있다. 현재 표본을 게임 제한이나 모바일 합격선으로 채택하지 않는다.
- 최종 모바일 성능·터치·발열은 빌드와 실기기 요청이 있을 때 검증한다. 현재 결과는 그 판정을 대체하지 않는다.
