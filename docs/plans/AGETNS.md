# PLAN 관리 지침

PLAN은 검증 가능한 작업 단위의 목표·범위·현재 진행·다음 행동을 기록한다.
전체 구현 순서와 기획상 완료 기준은 [구현 로드맵](../game-design/05-development/02-implementation/roadmap.md)을 따른다.
이 지침은 [루트 MAP](../../AGENTS.md)에서 명시적으로 읽으며, PLAN 목록은 [README](README.md)에서 찾는다.

## 현재 작업 찾기

- 실제 PLAN은 이 디렉터리의 `PLAN-NNN-주제.md` 파일이다. README·AGETNS·템플릿은 PLAN이 아니다.
- 타입과 상태의 원본은 각 PLAN 상단의 `type`·`status` 필드다. README의 type·status 열은 원본을 보여주는 요약이다.
- PLAN 생성·타입 변경·상태 전환 시 [PLAN 목록 README](README.md)도 반드시 함께 갱신한다.
- PLAN 상태를 바꾸면 [구현 로드맵](../game-design/05-development/02-implementation/roadmap.md)의 현재 작업·작업 PLAN 연결과 [기획 MAP README](../game-design/README.md)의 관련 상태 요약도 같은 변경에서 반드시 반영한다. 후보·진행·완료 표기를 원본과 맞추고, 단계 완료는 검증 결과에 따라 별도로 판정한다.
- 검사기로 PLAN 원본과 목록의 일치를 확인하고, 로드맵과 기획 MAP의 상태 표기도 직접 대조한다.
- 저장소 루트에서 `node scripts/validate-agent-docs.mjs`를 실행해 `active` PLAN이 최대 1개인지 확인한다. 0개는 정상 대기 상태이며 2개 이상은 오류다.
- 실행 가능한 PLAN은 승인된 `active` PLAN뿐이다. 0개이면 PLAN 실행을 시작하지 않고, 2개 이상이면 상태를 정리한 뒤 진행한다. 문서·작업 관리·독립 Sprite 작업은 [작업 절차](../agents/workflow.md)를 따른다.
- 상태 전환과 문서 체계 복구는 [작업 절차](../agents/workflow.md)에 따른다.

## PLAN 목록 README의 역할

- [README](README.md)는 PLAN 목록과 상태 추적 전용이다. 제목과 PLAN 링크·작업 단위·type·status로 구성된 목록 표만 유지한다.
- 개별 PLAN의 진행 설명·작업 결과·검증 수치·증거 링크·막힌 점·후속 제안이나 별도 상태 요약 문단을 추가하지 않는다. 이 내용은 해당 PLAN 본문에 기록하고, 상세 증거는 PLAN에서 연결한다.

## 타입과 완료 판정

모든 PLAN은 `type`을 필수로 기록하고 다음 소문자 값 중 하나를 사용한다. 타입은 작업의 주목적으로 구분하며 status와 별개다.

| 정확한 값 | 작업의 주목적 | 완료 판정 |
| --- | --- | --- |
| `development` | 기능·기반 시스템·환경·문서·저장소 등 일반 개발 | 본래 범위의 작업과 필수 기능·검증을 충족하면 completed |
| `art` | 정식 아트의 적용·교체 등 아트 변경 | 해당 범위의 필수 아트 적용·기술 검증·사용자 시각 확인을 모두 마치면 completed |

- `development`는 정식 아트의 미수령·교체 대기·사용자 시각 확인 대기가 완료를 막지 않는다. 필요한 기능 검증은 `Temp_` 에셋으로도 실제 충족해야 하며, 미구현 기능·실패한 검증을 아트 대기로 대신하지 않는다.
- `art`는 다른 요청의 완료를 기다리지 않고 자기 범위만 판정한다. 자기 범위의 필수 아트가 미완료이면 completed로 바꾸지 않는다.
- `art`의 작업·검증 순서는 [전체 리소스 작업 완료 후 테스트 원칙](../agents/verification.md#art-plan-test-readiness)을 따른다. PLAN에는 필수 리소스별 제작·수령·적용 상태와 테스트 시작 조건을 기록한다.
- 기능 개발 중 Sprite가 필요해졌다는 이유만으로 type을 art로 바꾸거나 아트 수령용 PLAN을 자동 생성하지 않는다. 타입을 완료 조건 우회 수단으로 바꾸지 않는다.
- 완료된 development PLAN은 남은 아트 요청 때문에 재활성화하거나 미완료로 되돌리지 않는다. 과거 검증 결과와 완료 기록은 보존한다.

## 독립 Sprite 요청과 PLAN의 관계

- 기존 규격의 Sprite 요청·수령·적용·검증은 [아트 요청 절차](../agents/art-assets.md#sprite-requests)로 독립 관리하며 새 PLAN 생성·활성화가 필요하지 않다.
- Require 폴더의 PLAN 번호는 요청 출처다. 요청 상태와 적용 결과는 해당 README에 기록하며, 출처 PLAN을 활성화하거나 그 완료 판정에 연결하지 않는다.
- 사용자가 명시적으로 `art` PLAN으로 관리하는 작업은 해당 PLAN이 승인되어 유일한 active가 된 뒤 그 범위에서 실행한다. 독립 요청 규칙으로 이 승인 절차를 우회하지 않는다.
- 아트 적용에 새로운 게임 규칙·코드 기능·패키지 도입이 필요하면 독립 요청 범위에 섞지 않고 기존 PLAN 생성·승인 절차를 따른다.
- 독립 요청만 처리할 때 active가 0개여도 PLAN을 만들거나 활성화하지 않는다. 검사 결과에 실제 오류가 있으면 확인·수정하고 보고한다.

## 상태

| 정확한 값 | 의미 |
| --- | --- |
| `proposed` | 후보 작업. 구현에 착수하지 않는다. |
| `active` | 현재 유일한 작업 대상. 미실행 단계가 있을 수 있다. |
| `completed` | 범위 안의 작업과 필수 검증이 완료되고 증거가 남았다. |
| `rejected` | 채택하지 않거나 취소한 작업. 이유를 남긴다. |
| `on hold` | 보류한 작업. 중단 지점·이유·재개 조건을 남긴다. |

상태는 소문자와 공백까지 위 표대로 사용한다. `blocked`, `done`, `paused` 등을 추가하지 않는다.
막힌 이유는 PLAN 본문에 기록하며 상태를 임의로 늘리지 않는다.

## 생성과 활성화 승인

- 모든 새 PLAN의 최초 상태는 `proposed`다. 생성과 동시에 `active`로 지정하지 않는다.
- 사용자가 해당 PLAN의 실행·활성화 또는 재개를 명시적으로 승인한 경우에만 `active`로 전환한다. 승인 근거를 PLAN의 상태 전환 기록에 남긴다.
- 로드맵 순서, 선행 PLAN 완료, 후보 작성, 에이전트의 판단만으로 다음 PLAN을 자동 활성화하지 않는다.
- 승인 없이 `proposed` 또는 `on hold`를 `active`로 바꾸지 않는다. active가 0개인 정상 대기 상태를 채우기 위해 임의 활성화하지 않는다.

## 템플릿 선택

| 작업의 주된 대상 | 복사할 템플릿 | 중점 명세 |
| --- | --- | --- |
| 일반 개발·문서·환경 | [공통 개발](_template.md) | 기능·변경 범위와 검증 |
| 애니메이션이 있는 인게임 아트 | [애니메이션 아트](_template-art-animation.md) | 방향·동작·프레임 수, 게임 상태/사건과 재생 연결 |
| UI 아이콘·버튼·패널·HUD 아트 | [UI 아트](_template-art-ui.md) | 사용 화면·상태별 표현·크기 조절·텍스트·터치 영역 |
| 애니메이션이 없는 인게임 아트 | [정적 인게임 아트](_template-art-static.md) | 바닥/타일 연결·변형, 건물/오브젝트 점유·회전·가려짐 |

- 세 아트 양식의 메타데이터는 모두 `type: art`, 최초 상태는 `proposed`다. 템플릿 구분을 새 PLAN type이나 상태 값으로 만들지 않는다.
- UI는 애니메이션 유무와 관계없이 UI 양식을 우선한다. 프레임 애니메이션이 있으면 애니메이션 양식의 동작별 움직임 설명·재생 연결 표를 추가하고, 단순 UI 전환은 UI 양식의 상태 표현에 기록한다.
- 정적 인게임 아트의 방향별 원화·회전·변형은 시간에 따른 애니메이션과 구분한다. 바닥과 건물 중 해당하는 항목만 작성한다.
- 여러 종류가 하나의 작업을 이루면 주된 대상의 양식에 필요한 표를 합친다. 양식 수에 맞추어 PLAN을 강제로 나누거나 각 양식의 모든 검증을 합산하지 않는다.

## 아트 템플릿 작성 기준

- 현재 확정 명세·진행을 앞에, 이전 제안·변경 이유·상태 전환 이력을 뒤에 둔다. 미정·제안·확정값을 구분하고 예시 수치·동작을 승인된 요구로 복사하지 않는다.
- PLAN에는 범위·디자인 의도와 원하는 모습·산출물 요약·사용처별 적용·검증·완료 판단을 둔다. 상세 제작 명세·요청별 수령/수정/적용 이력은 [Sprite 요청 README](../agents/art-assets.md#sprite-requests)를 원본으로 연결한다. 기존 요청 ID와 제작 기록을 재사용한다.
- 디자인 설명은 에셋별 인상·실루엣·구성·색/재질·시점/명암·강조/생략 요소를 문장으로 요약하고, 참고 자료에서 가져올 요소와 적용하지 않을 요소를 명시한다. 링크나 규격표만으로 대신하지 않는다. 애니메이션은 동작별 원하는 움직임·변형/고정 부위·리듬을 재생 조건과 함께 기록한다.
- 제작 작업공간은 `C:/Dev/Unity/Art`다. [Art 디자인 MAP](../../../Art/docs/agetns/design/README.md)·[제작 MAP](../../../Art/docs/agetns/creation/README.md)·필요 시 [애니메이션 MAP](../../../Art/docs/agetns/animation/README.md)의 해당 문서를 읽고 채택한 기준/버전·적용 범위를 연결한다. 공통 규칙 전문·개별 좌표/색상/프레임 상세는 복제하지 않는다.
- Art 공통값의 미정 표기는 개별 에셋의 기존 사용자 승인값을 취소하지 않는다. 대상에 적용되는 승인 근거를 확인하고 제안값과 구분한다. Art PLAN·asset_id·리비전과 Unity 요청 ID의 대응은 [전달 지침](../../../Art/docs/agetns/production/export-and-handoff.md)을 따른다.
- 제작 담당·위임 근거·현재 실행 범위·사용자가 보류한 단계를 기록한다. 기존 승인은 계속 유효하며 템플릿의 체크 항목만을 이유로 같은 승인을 반복 요청하지 않는다.
- 에셋 종류·변형·방향·동작별 프레임·총 프레임/셀·시트/출력 파일 수를 구분한다. 원본 캔버스·불투명 영역·게임 점유·화면 표시·입력 영역도 구분한다. 공통 PPU·임포트값은 [아트 지침](../agents/art-assets.md)을 참조한다.
- 수령·적용·승인 리비전과 원본 시각 승인·실제 게임 화면 승인을 구분한다. 전체 필수 리소스의 준비 판정은 [테스트 시작 조건](../agents/verification.md#art-plan-test-readiness)에 따라 날짜·근거·남은 항목을 기록한다.
- 검증은 현재 제품 기능과 변경 영향에 맞게 고른다. 과거 PLAN의 폐기된 조작·테스트 수·특정 배율을 그대로 요구하지 않는다. 테스트 전후 원본·참조·저장/설정·Editor 환경의 보존과 복원 결과도 남긴다.
- 완료 시 적용 리비전·사용자 게임 화면 확인·채택 규격·실제 완료한 로드맵 범위·남은 후속 범위를 기록한다. [PLAN-026](PLAN-026-art-style-scale-and-sample-integration.md)·[PLAN-029](PLAN-029-laboratory-processing-cultivation-storage-art.md)는 사례이며 현재 규칙의 원본은 각 지침이다.

## 결과물 위치 지정

- 모든 PLAN은 작성 시 「결과물 저장 위치」를 두고 산출물별 **기준 루트·디렉터리·파일명·확장자**를 지정한다. 폴더 이름만 적거나 실행 때 정한다는 문장으로 대신하지 않는다. 해당 없음은 사유를 적는다.
- 아트 PLAN은 에셋/요청별 작업용 Art 원본, 리비전 원본 보존본·PNG 출력·제출 README, Unity 수령 파일, 최종 적용 파일, 원본 비교/게임 화면/검증 자료 위치를 모두 대응시킨다.
- Art 원본/제출본은 [Art 구조](../../../Art/docs/agetns/project-structure.md)의 `assets/<종류>/<AssetId>/source/`·`revisions/rNNN/`를 사용한다. Unity에 적용할 아트 PNG/시트는 `UnityProject/Assets/Sprites/` 아래 Creature·Facility·Resource·World·UI·VFX 등 실제 카테고리에 둔다.
- Unity 수령은 `Assets/Sprites/Require/PLAN-NNN/<요청 ID>/rNNN/<파일명>`로 지정한다. 최초 예정 리비전과 요청 ID를 명시하고, 기존 요청은 재사용한다. 새 ID의 경로 배정과 상세 요청 발행·실제 수령은 구분한다.
- 검수 자료는 `docs/plans/evidence/PLAN-NNN/` 아래 색인·리비전/경로 목록·원본 비교·실행별 화면/영상·테스트 결과·로그·사용자 승인·환경 복원으로 구분하고 구체 파일명을 적는다. 원본 Art 증거는 중복 복사 대신 실제 경로로 연결할 수 있다.
- `r001`·`run-001` 등 최초 위치를 명시하고 이후 리비전/실행 번호 증가 규칙을 적는다. 이전 제출/검수 자료를 덮어쓰지 않는다. 선택 검증/재사용으로 미생성인 파일은 사유와 실제 참조를 기록한다.
- 재사용 전용/통합 검수 PLAN은 원본 경로 표를 연결하고 자체 검수 결과 경로를 지정한다. 중복 원본·요청·PNG를 만들지 않는다. 재질/프리팹/코드는 [프로젝트 구조](../agents/project-structure.md)의 해당 에셋 종류에 두며 Sprites에 섞지 않는다.
- 미생성 위치는 코드 표기로 `예정`임을 명시한다. 경로 지정만으로 빈 폴더·가상 산출물을 만들지 않으며, 생성 후 실제 링크·리비전·변경된 위치를 PLAN과 요청 README에 반영한다.

## 작성과 기록

1. [템플릿 선택](#template-selection)에서 해당 양식을 복사하고 고유한 PLAN ID와 파일명을 부여한다.
2. 주목적에 맞는 `type`과 목표·범위·기준 문서·[결과물 위치](#artifact-locations)·완료 조건·검증 방법을 작성한다. 모든 새 PLAN은 `proposed`로 두고 위 승인 규칙을 따른다.
3. 전체 단계를 하나의 거대한 PLAN으로 만들지 않고 검증 가능한 결과로 나눈다.
4. 체크리스트·현재 상황·다음 행동·검증 결과는 해당 PLAN 한 곳에서 갱신한다.
5. 상세 로그는 산출물로 보관하고 실행 환경·결과·증거 위치를 PLAN에 연결한다.
6. 구조에 영향을 주는 기술 선택은 [기술 결정](../decisions/README.md)에, 작은 구현 선택은 PLAN에 기록한다.

초기 기능 구현·기존 코드 변경의 추상화와 재사용 범위는 [추상화 기준](../agents/abstraction.md)을 적용한다. 도입·유보 근거와 검증은 해당 PLAN에 변경 규모에 맞춰 기록한다.

검증 범위·필수 완료 조건을 작성할 때 [빌드 테스트 실행 조건](../agents/verification.md#build-test-authorization)의 기본 제외 원칙을 따른다. 빌드를 포함하는 경우 해당 빌드에 대한 사용자 요청·승인 근거를 기록한다.
고부하 테스트도 [고부하 테스트 실행 조건](../agents/verification.md#load-test-authorization)에 따라 명시적 요청이 있을 때만 포함한다. 일반 PLAN 실행·재개 승인으로 이를 대신하지 않으며, 요청이 없으면 기본 검증·필수 완료 조건에서 제외하고 미측정 한계를 남긴다.

`active` 지정은 작업 대상을 선택하는 것이며 설치·배포·범위 확장 등 새로운 권한을 부여하지 않는다.
이전 PLAN의 완료는 다음 PLAN의 실행·검증 완료를 의미하지 않는다.
