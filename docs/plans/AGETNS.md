# PLAN 관리 지침

PLAN은 검증 가능한 작업 단위의 목표·범위·현재 진행·다음 행동을 기록한다.
전체 구현 순서와 기획상 완료 기준은 [구현 로드맵](../game-design/05-development/02-implementation/roadmap.md)을 따른다.
이 지침은 [루트 MAP](../../AGENTS.md)에서 명시적으로 읽으며, PLAN 목록은 [README](README.md)에서 찾는다.

## 현재 작업 찾기

- 실제 PLAN은 이 디렉터리의 `PLAN-NNN-주제.md` 파일이다. README·AGETNS·템플릿은 PLAN이 아니다.
- 타입과 상태의 원본은 각 PLAN 상단의 `type`·`status` 필드다. README의 type·status 열은 원본을 보여주는 요약이다.
- PLAN 생성·타입 변경·상태 전환 시 [PLAN 목록 README](README.md)도 반드시 함께 갱신한다.
- PLAN 상태를 바꾸면 [구현 로드맵](../game-design/05-development/02-implementation/roadmap.md)의 현재 작업·작업 PLAN 연결과 [기획 MAP README](../game-design/README.md)의 관련 상태 요약도 같은 변경에서 반드시 반영한다. 후보·진행·완료 표기를 원본과 맞추고, 단계 완료는 검증 결과에 따라 별도로 판정한다.
- 검사기로 PLAN 원본과 목록의 일치를 확인하고, 로드맵과 기획 MAP의 상태 표기도 직접 대조한다.
- 저장소 루트에서 `node scripts/validate-agent-docs.mjs`를 실행해 유일한 `active` PLAN을 확인한다.
- 작업 가능한 PLAN은 `active` 하나뿐이다. 개수가 0개 또는 2개 이상이면 기능 작업을 시작하지 않는다.
- 상태 전환과 문서 체계 복구는 [작업 절차](../agents/workflow.md)에 따른다.

## PLAN 목록 README의 역할

- [README](README.md)는 PLAN 목록과 상태 추적 전용이다. 제목과 PLAN 링크·작업 단위·type·status로 구성된 목록 표만 유지한다.
- 개별 PLAN의 진행 설명·작업 결과·검증 수치·증거 링크·막힌 점·후속 제안이나 별도 상태 요약 문단을 추가하지 않는다. 이 내용은 해당 PLAN 본문에 기록하고, 상세 증거는 PLAN에서 연결한다.

## 타입과 완료 판정

모든 PLAN은 `type`을 필수로 기록하고 다음 소문자 값 중 하나를 사용한다. 타입은 작업의 주목적으로 구분하며 status와 별개다.

| 정확한 값 | 작업의 주목적 | 완료 판정 |
| --- | --- | --- |
| `development` | 기능·기반 시스템·환경·문서·저장소 등 일반 개발 | 본래 범위의 작업과 필수 기능·검증을 충족하면 completed |
| `art` | 정식 아트의 적용·교체 등 아트 변경 | 해당 범위의 필수 아트 적용·기술 검증·사용자 시각 확인을 모두 마치면 completed |

- `development`는 정식 아트의 미수령·교체 대기·사용자 시각 확인 대기가 완료를 막지 않는다. 필요한 기능 검증은 `Temp_` 에셋으로도 실제 충족해야 하며, 미구현 기능·실패한 검증을 아트 대기로 대신하지 않는다.
- `art`는 다른 요청의 완료를 기다리지 않고 자기 범위만 판정한다. 자기 범위의 필수 아트가 미완료이면 completed로 바꾸지 않는다.
- 기능 개발 중 Sprite가 필요해졌다는 이유만으로 type을 art로 바꾸거나 아트 수령용 PLAN을 자동 생성하지 않는다. 타입을 완료 조건 우회 수단으로 바꾸지 않는다.
- 완료된 development PLAN은 남은 아트 요청 때문에 재활성화하거나 미완료로 되돌리지 않는다. 과거 검증 결과와 완료 기록은 보존한다.

## 독립 Sprite 요청과 PLAN의 관계

- 기존 규격의 Sprite 요청·수령·적용·검증은 [아트 요청 절차](../agents/art-assets.md#sprite-requests)로 독립 관리하며 새 PLAN 생성·활성화가 필요하지 않다.
- Require 폴더의 PLAN 번호는 요청 출처다. 요청 상태와 적용 결과는 해당 README에 기록하며, 출처 PLAN을 활성화하거나 그 완료 판정에 연결하지 않는다.
- 사용자가 명시적으로 `art` PLAN으로 관리하는 작업은 해당 PLAN이 승인되어 유일한 active가 된 뒤 그 범위에서 실행한다. 독립 요청 규칙으로 이 승인 절차를 우회하지 않는다.
- 아트 적용에 새로운 게임 규칙·코드 기능·패키지 도입이 필요하면 독립 요청 범위에 섞지 않고 기존 PLAN 생성·승인 절차를 따른다.
- 독립 요청만 처리할 때 active가 0개여도 PLAN을 만들거나 활성화하지 않는다. 검사기의 active 개수 오류와 다른 문서 오류를 구분해 보고한다.

## 상태

| 정확한 값 | 의미 |
| --- | --- |
| `proposed` | 후보 작업. 구현에 착수하지 않는다. |
| `active` | 현재 유일한 작업 대상. 미실행 단계가 있을 수 있다. |
| `completed` | 범위 안의 작업과 필수 검증이 완료되고 증거가 남았다. |
| `rejected` | 채택하지 않거나 취소한 작업. 이유를 남긴다. |
| `on hold` | 보류한 작업. 중단 지점·이유·재개 조건을 남긴다. |

상태는 소문자와 공백까지 위 표대로 사용한다. `blocked`, `done`, `paused` 등을 추가하지 않는다.
막힌 이유는 PLAN 본문에 기록하며 상태를 임의로 늘리지 않는다.

## 생성과 활성화 승인

- 모든 새 PLAN의 최초 상태는 `proposed`다. 생성과 동시에 `active`로 지정하지 않는다.
- 사용자가 해당 PLAN의 실행·활성화 또는 재개를 명시적으로 승인한 경우에만 `active`로 전환한다. 승인 근거를 PLAN의 상태 전환 기록에 남긴다.
- 로드맵 순서, 선행 PLAN 완료, 후보 작성, 에이전트의 판단만으로 다음 PLAN을 자동 활성화하지 않는다.
- 승인 없이 `proposed` 또는 `on hold`를 `active`로 바꾸지 않는다. `active`가 없어 검사기가 오류를 보고하더라도 검사 통과를 위해 임의 활성화하지 않고 기능 작업을 멈춘다.

## 작성과 기록

1. [_template.md](_template.md)를 복사하고 고유한 PLAN ID와 파일명을 부여한다.
2. 주목적에 맞는 `type`과 목표·범위·기준 문서·완료 조건·검증 방법을 작성한다. 모든 새 PLAN은 `proposed`로 두고 위 승인 규칙을 따른다.
3. 전체 단계를 하나의 거대한 PLAN으로 만들지 않고 검증 가능한 결과로 나눈다.
4. 체크리스트·현재 상황·다음 행동·검증 결과는 해당 PLAN 한 곳에서 갱신한다.
5. 상세 로그는 산출물로 보관하고 실행 환경·결과·증거 위치를 PLAN에 연결한다.
6. 구조에 영향을 주는 기술 선택은 [기술 결정](../decisions/README.md)에, 작은 구현 선택은 PLAN에 기록한다.

`active` 지정은 작업 대상을 선택하는 것이며 설치·배포·범위 확장 등 새로운 권한을 부여하지 않는다.
이전 PLAN의 완료는 다음 PLAN의 실행·검증 완료를 의미하지 않는다.
