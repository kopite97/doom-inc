# PLAN 관리 지침

PLAN은 검증 가능한 작업 단위의 목표·범위·현재 진행·다음 행동을 기록한다.
전체 구현 순서와 기획상 완료 기준은 [구현 로드맵](../game-design/05-development/02-implementation/roadmap.md)을 따른다.
이 지침은 [루트 MAP](../../AGENTS.md)에서 명시적으로 읽으며, PLAN 목록은 [README](README.md)에서 찾는다.

## 현재 작업 찾기

- 실제 PLAN은 이 디렉터리의 `PLAN-NNN-주제.md` 파일이다. README·AGETNS·템플릿은 PLAN이 아니다.
- 상태의 원본은 각 PLAN 상단의 `status` 필드다. README의 status 열은 원본을 보여주는 요약이다.
- PLAN 생성·상태 전환 시 README 목록도 함께 갱신한다. 검사기로 원본과 목록의 일치를 확인한다.
- 저장소 루트에서 `node scripts/validate-agent-docs.mjs`를 실행해 유일한 `active` PLAN을 확인한다.
- 작업 가능한 PLAN은 `active` 하나뿐이다. 개수가 0개 또는 2개 이상이면 기능 작업을 시작하지 않는다.
- 상태 전환과 문서 체계 복구는 [작업 절차](../agents/workflow.md)에 따른다.

## 상태

| 정확한 값 | 의미 |
| --- | --- |
| `proposed` | 후보 작업. 구현에 착수하지 않는다. |
| `active` | 현재 유일한 작업 대상. 미실행 단계가 있을 수 있다. |
| `completed` | 범위 안의 작업과 필수 검증이 완료되고 증거가 남았다. |
| `rejected` | 채택하지 않거나 취소한 작업. 이유를 남긴다. |
| `on hold` | 보류한 작업. 중단 지점·이유·재개 조건을 남긴다. |

상태는 소문자와 공백까지 위 표대로 사용한다. `blocked`, `done`, `paused` 등을 추가하지 않는다.
막힌 이유는 PLAN 본문에 기록하며 상태를 임의로 늘리지 않는다.

## 작성과 기록

1. [_template.md](_template.md)를 복사하고 고유한 PLAN ID와 파일명을 부여한다.
2. 목표·범위·기준 문서·완료 조건·검증 방법을 작성한다. 새 후보는 `proposed`로 둔다.
3. 전체 단계를 하나의 거대한 PLAN으로 만들지 않고 검증 가능한 결과로 나눈다.
4. 체크리스트·현재 상황·다음 행동·검증 결과는 해당 PLAN 한 곳에서 갱신한다.
5. 상세 로그는 산출물로 보관하고 실행 환경·결과·증거 위치를 PLAN에 연결한다.
6. 구조에 영향을 주는 기술 선택은 [기술 결정](../decisions/README.md)에, 작은 구현 선택은 PLAN에 기록한다.

`active` 지정은 작업 대상을 선택하는 것이며 설치·배포·범위 확장 등 새로운 권한을 부여하지 않는다.
이전 PLAN의 완료는 다음 PLAN의 실행·검증 완료를 의미하지 않는다.
