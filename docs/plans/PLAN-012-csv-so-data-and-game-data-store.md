# PLAN-012 CSV·SO 분리와 GameDataStore 초기 로딩

## 목표

밸런스와 일반 값은 로컬 CSV에서 편집하고, SO는 Unity 에셋 참조를 담당한다. 게임 초기 로딩에서 CSV와 SO를 정의 ID로 결합한 읽기 전용 Data 전체를 `GameDataStore`에 저장한 뒤 Runtime을 생성한다.

`GameDataStore`는 씬 전환과 한 판 재시작에도 유지되는 단일 인스턴스다. CSV 취득 경계는 비동기 인터페이스로 분리하여, 향후 Google Sheets 기반 API 공급자로 교체해도 파서·Data 결합·게임 로직을 변경하지 않도록 한다.

## 범위

- 포함: 현재 게임 정의 SO 10개와 코드에 있는 관련 밸런스 값의 조사·이관, CSV 스키마·로컬 공급자, 결합 Data·검증, 영속 싱글턴, 초기 로딩, Thing·Factory·Manager·UI·하네스·저장 복원·Editor 생성 도구의 참조 전환과 회귀 검증.
- 포함: 데이터 변경과 저장 호환성 정책, CSV 편집 안내, 사용자 요청에 맞춘 기획·기술 결정·작업 지침의 정의 책임 정비.
- 제외: 실제 Google Sheets 연결·API 서버·인증·배포·원격 캐시·운영 도구, 플레이 중 데이터 갱신, 신규 콘텐츠·아트, 수치 재밸런싱, 전체 Runtime의 Unity 타입 제거.
- 제외: 로드맵 4단계의 세로 대응·모바일 최종 빌드/실기기·성능 종합 검증. 이번 데이터 로딩의 Player 호환성 확인과 최종 모바일 완료 판정은 구분한다.
- 작업 요청·위임 근거: 2026-10-28 사용자가 `CSV + SO → Data → Runtime`, 교체 가능한 CSV 취득부, 초기 전체 로딩과 파괴되지 않는 `GameDataStore` 싱글턴을 지정하고 PLAN-012 작성을 요청했다. 동일 날짜에 두 검토 사항의 보완과 실행을 명시적으로 승인했다.

## 이관 전 구조와 대상

이관 전 `Thing.Definition`은 SO를 직접 참조했다. 새 게임은 SO를 Factory에 전달하고, 이어하기는 SO 정의 목록과 저장 DTO를 Codec에서 결합한다. 현재 `Data` 폴더는 결합 결과 계층을 뜻하지 않는다.

| 현재 원본 | CSV로 옮길 값·관계 | 이관 시 보존할 조건 |
| --- | --- | --- |
| 공통 Thing 정의 | 정의 ID, 표시 이름, 컴포넌트 종류 | 기존 ID와 종류를 유지하고 같은 정의를 공유 |
| 자원 2종 | 유기물·배양액 식별 정보 | 실행 중 수량·보관처는 Runtime 소유 |
| 생명체 3종 | 역할, 운반량, 칸당 이동시간 | 현재 운반량 5·이동시간 0.25초, 역할별 작업 가능 조건 유지 |
| 시설 4종 | 역할, 점유 폭·높이, 상호작용 상대 좌표, 건설 자원 ID·비용·작업시간, 저장 용량, 획득 수량·시간 | 건설 비용 2·작업 3초, 저장 용량 20, 획득 5개/5초 등 현재 에셋 값 보존 |
| 가공·배양 설정 | 투입·산출 자원/생명체 ID, 투입·산출량, 생산 작업시간 | 가공 유기물 5→배양액 1/10초, 배양 배양액 2→선택 개체 1/20초, 회차·입고 규칙 유지 |
| 침공 설정 1개 | 활동 주기, 소규모·주요 성과, 주요 성과 간격, 목표, 상세 보고 경계, 보고 보관 수 | 현재 5초·2·10·4회·120·60·20 및 저장된 한 판 설정의 의미 보존 |
| 코드의 게임 조정값 | 유인/무인 생산 배율, 시작 Map 크기, 시작 배치 좌표, 멸망 연출 시간 등 | 현재 100%/20%, 16×10, 연출 4초 등을 목록화하고 같은 값으로 이관 |

- 역할별로 쓰지 않는 시설 필드의 기존 기본값을 새 기능으로 해석하지 않는다. 필수·선택·미사용 열과 관계를 구분하고 생산·배양 산출량 1 등의 현재 규칙을 검증한다.
- 시작 유기물은 현재 두 초기 시설의 건설비 합으로 계산된다. 이를 고정 CSV 값 4로 중복 저장하지 않고 파생 규칙으로 유지한다. 초기 운반량·배치·시설 크기와의 정합성도 검사한다.
- `Vector2Int`로 저장한 정의 좌표는 CSV의 정수 열로 표현한다. Runtime에서 필요한 공간 자료형으로 바꾸는 것은 소비 경계의 책임이다.
- ID·enum·문자열·연결 ID도 CSV 스키마에 포함한다. 메서드로 계산하는 `CanWork` 등의 규칙은 중복 열로 만들지 않는다.
- 저장 형식 버전·수치 오차 허용치·프레임 처리 상한·자동 저장 주기 같은 기술 정책은 밸런스와 구분하여 코드/설정에 유지하고 제외 이유를 목록에 남긴다. 모든 숫자 리터럴을 일괄 CSV화하지 않는다.
- 현재 게임 SO에는 Sprite·Prefab·Material·Audio 참조가 없고 다른 게임 정의 SO 참조가 있다. 이 관계는 CSV의 정의 ID로 옮긴다. 결합용 ID와 실제 필요한 Unity 에셋 참조만 SO에 남기며, 이번 작업 때문에 새 아트를 요구하거나 가짜 필수 참조를 만들지 않는다.
- URP·렌더러·입력 등 Unity 도구 설정 SO는 이관 대상이 아니다.

## 목표 구조와 계약

### 취득·파싱·결합의 분리

```text
ICsvDataSource.LoadAsync(cancellationToken)
  └─ 로컬 CSV 공급자 / 향후 API 공급자
        ↓ 테이블별 CSV 원문 + 출처·데이터 묶음 식별 정보
CSV 파서 → 행 DTO → 스키마·관계 검증 ─┐
주제별 SO Registry → ID·참조 검증 ──┤
                                   ↓
                         읽기 전용 결합 Data 전체
                                   ↓ 검증 성공 시 한 번에 공개
                   GameDataStore [Ready / 영속 싱글턴]
                                   ↓ 읽기 전용 의존성 전달
                    Factory·저장 복원 → Runtime
```

인터페이스명은 설계안이며 `GameDataStore` 이름은 사용자 지정이다. CSV 행 DTO와 진행 상태를 저장하는 Snapshot DTO는 별도 자료형·책임으로 유지한다.

- 공급자는 CSV를 가져오기만 한다. 공급자 인터페이스의 입력·출력과 공통 파서는 Unity에 의존하지 않는다. 로컬 공급자 구현 내부에서는 TextAsset을 읽을 수 있지만 생명체·시설·자원 SO 조회, Data 결합·Runtime 생성·저장 복원은 수행하지 않는다. 비동기 완료·취소·오류를 전달하고 파서가 파일 경로나 HTTP 응답 객체에 의존하지 않도록 한다.
- 여러 테이블은 하나의 완전한 묶음으로 전달한다. 필수 테이블 집합·스키마 버전·묶음 식별 정보와 콘텐츠 해시를 검사하여 테이블 일부만 바뀐 상태가 공개되지 않도록 한다.
- 향후 API 공급자는 Google Sheets 응답을 같은 CSV 묶음 계약으로 변환한다. 원격 여러 테이블의 동일 배포 버전 확보는 공급자 책임이다. 인증·재시도·캐시 정책은 원격 구현 PLAN에서 정한다.
- 이번에는 실제 로컬 공급자와 메모리 기반 테스트 공급자를 구현한다. 지연·취소·실패·같은 데이터 반환을 주입하여 교체 가능성을 검증한다.
- 로컬 원본의 예정 위치는 `UnityProject/Assets/CSV/Balance/`다. Unity에 포함되는 CSV 텍스트 에셋 참조를 로컬 공급자에 전달하는 방식을 우선하며, 로컬 목록 SO를 쓰더라도 파일 참조만 담는다. 새 경로를 프로젝트 구조 지침에 등록한다.
- 파일 시스템 절대 경로·Editor의 AssetDatabase를 런타임 취득 계약에 노출하지 않는다. 실제 임포트·Player 포함 방식과 Android 호환성을 확인해 기술 결정에 남기며, 경로/패키징 선택이 바뀌어도 공급자 밖의 계약은 유지한다.

### 주제별 SO Registry와 초기화 연결

2026-10-28 사용자가 제안한 주제별 Registry SO를 결합 입력으로 사용한다. 현재 `LaboratoryView`의 개별 SO 참조 10개를 초기화 전용 클래스의 주제별 Registry 참조로 정리하는 방향이다. 아래 이름은 구현 시 역할을 확인할 설계안이다.

| 구성 | 보유할 내용 | 책임 |
| --- | --- | --- |
| `CreatureDefinitionRegistry` SO | 생명체 SO 목록 | 생명체 에셋의 명시적 등록 |
| `FacilityDefinitionRegistry` SO | 시설 SO 목록 | 시설 에셋의 명시적 등록 |
| `ResourceDefinitionRegistry` SO | 자원 SO 목록 | 자원 에셋의 명시적 등록 |
| `GameBootstrap` | 위 Registry의 직렬화 필드, CSV 공급자 구성 | 취득·검증·결합·Store 준비·세션 시작 순서 조율 |
| `GameDataComposer` | 호출로 전달받은 DTO와 Registry 항목 | 정의 ID 결합·타입/관계 검증·읽기 전용 Data 후보 생성 |

- Registry는 해당 타입의 SO 목록만 보유한다. 밸런스 값을 복제하거나 결합 Data·Runtime·로딩 진행 상태를 저장하지 않으며, Registry 자체를 싱글턴으로 만들지 않는다. 등록된 SO에서 ID를 읽고 Registry에 별도 ID 문자열을 중복 입력하지 않는다.
- 개별 SO는 결합용 `DefinitionId`와 Unity 에셋 참조를 가진다. “같은 ID”는 같은 정의의 두 입력이라는 뜻이며, CSV의 수치와 SO의 에셋 필드를 서로 비교하거나 하나로 덮어쓰는 의미가 아니다.
- 자원·시설·생명체는 CSV 행과 Registry 등록 SO가 ID별로 정확히 1:1 대응해야 한다. 현재 그림이 없는 정의도 SO 항목은 등록하고 선택적 에셋 필드만 비워 둔다. 숫자 전용 침공·공통 설정에는 불필요한 SO/Registry를 만들지 않는다.
- 시작 시 Registry 누락, null 항목, 같은 SO 중복 등록, CSV/Registry 각각의 중복 ID, 다른 주제 간 ID 충돌, 종류 불일치와 한쪽에만 있는 ID를 검사한다. 기존의 전역 고유 정의 ID를 유지하고 대소문자를 구분하는 정확한 비교를 사용한다. 목록 순서·파일명·표시 이름은 결합 키로 사용하지 않는다.
- 조립기는 검증한 항목을 ID 사전으로 구성하여 결합한다. 모든 정의를 먼저 식별한 다음 시설의 투입 자원·배양 대상 같은 정의 간 관계를 해석하므로 CSV/Registry 순서가 결과에 영향을 주지 않는다. 완성 전 후보는 Store에 공개하지 않는다.
- Data에는 DTO 값을 복사하고 필요한 Unity 에셋 참조를 읽기 전용 바인딩으로 구성한다. 원본 DTO나 SO를 통한 가변 필드 조회를 게임 로직의 우회 경로로 남기지 않는다.
- 주제별 Registry 필드는 초기화 전용 클래스가 소유하며 화면 View는 준비된 데이터/세션을 받는다. Registry 필드 수가 실제로 커지기 전에는 이를 다시 감싸는 상위 Registry를 추가하지 않는다.
- 수동 등록 누락은 Editor 검사와 초기화 검사에서 동일한 검증기를 통해 알린다. 폴더 자동 검색을 실행 시 등록 원본으로 사용하지 않는다.
- 향후 API로 새 ID를 공급하더라도 대응 SO가 로컬 Registry에 없으면 로딩 오류다. 기존 콘텐츠의 값 변경과 신규 에셋 배포를 구분하며, 원격 에셋 전달은 별도 후속 범위다. Registry 참조가 많아질 때의 로딩 비용은 실제 콘텐츠 규모에 맞춰 검토한다.

### CSV 스키마와 결합 Data

- 자원·생명체·시설·침공·시작/공통 조정 설정을 테이블로 정의한다. 가공·배양은 시설 ID에 연결된 규칙으로 표현하고 같은 값의 원본을 여러 테이블에 두지 않는다. 구체적인 열·타입·단위·빈 값 규칙은 이관표와 함께 확정한다.
- UTF-8/BOM·한글·인용부호·쉼표·인용된 줄바꿈을 처리한다. 수치는 문화권에 독립적으로 읽고, 문자열/숫자 공백 규칙과 enum·컴포넌트 목록 표기를 문서화한다.
- 필수/중복/알 수 없는 헤더, 행 열 수, 중복·빈 ID, 숫자 범위·오버플로·NaN/Infinity, 정의 종류·역할·연결 ID, 공간·시작 조건과 현재 게임 규칙을 검증한다. 잘못된 값을 임의 기본값으로 보정하지 않는다.
- 기존 정의 ID를 대소문자까지 그대로 유지한다. CSV↔SO는 위 Registry의 1:1 규칙으로 결합하고 중복·누락·고아 참조를 검사한다. 선택적 에셋 참조의 빈 값과 필수 SO 등록 누락을 구분하며 숫자 전용 공통 설정에 불필요한 SO를 만들지 않는다.
- 오류는 테이블·행·열·정의 ID와 원인을 제공한다. CSV 문법, 수치, 참조, 에셋 결합 오류를 구분하여 사용자가 원본을 수정할 수 있게 한다.
- 결합 Data는 일반 C# 읽기 전용 객체로 만들고 컬렉션 내부도 외부에서 수정할 수 없게 한다. 게임 값과 Unity 에셋 바인딩을 구분하여 담고, 게임 로직은 값/정의만, 화면은 필요한 바인딩을 사용한다. 결합 Data 전체가 Unity와 무관한 타입이라고 가정하지 않는다.
- 런타임은 CSV 행 DTO나 원본 SO의 밸런스 필드를 직접 읽지 않는다. 시작 후 CSV·SO 원본을 변경해도 이미 공개된 Data 값이 바뀌지 않는다. Unity 에셋 객체를 복제하거나 실행 상태 저장소로 사용하지 않는다.

### GameDataStore 수명과 초기 로딩

- `GameDataStore`는 Unity 수명 연결을 가진 단일 인스턴스로 두고 `DontDestroyOnLoad`를 적용한다. 데이터 조회는 읽기 전용 계약으로 제공하고 파서·검증기·결합기는 일반 C#으로 분리한다.
- 실행 연결 코드는 `Presentation/Bootstrap` 등 기존 역할 분류에 배치한다. Core·Gameplay가 Presentation의 싱글턴 구현을 참조하지 않도록 완성된 Data 조회 계약을 생성자/Factory에 전달한다. 기존 Manager의 일반 C# 책임을 유지한다.
- 상태는 미초기화·로딩·준비 완료·실패를 구분한다. 로컬 데이터라도 취득 완료를 기다리고, 전체 테이블과 필요한 에셋 바인딩을 검증·결합한 후보가 완성된 뒤 한 번에 `Ready`로 공개한다.
- 중복 초기화 요청은 하나의 작업을 공유한다. 씬 전환으로 생긴 중복 인스턴스는 기존 유효 인스턴스를 유지한다. 종료·취소·재시도 뒤 도착한 오래된 완료가 데이터를 덮어쓰지 않게 한다.
- 준비 전에는 신규 세션 생성·이어하기·진행·자동 저장을 시작하지 않는다. 화면에는 로딩/오류와 재시도 경로를 제공하고, 하네스도 동일한 준비 상태를 확인한다. 실패 시 부분 Data나 임시 기본값으로 플레이하지 않는다.
- 직접 플레이 씬 진입과 씬 재진입도 같은 초기화 경계를 사용한다. 준비된 데이터는 씬 이동·이어하기·한 판 재시작에서 재사용하고, 한 실행 중 새 버전으로 바꾸지 않는다.
- `GameDataStore`에는 Thing·Map·재고·Job·세션·종료 요청 바인딩을 저장하지 않는다. 한 판 재시작은 기존 GameFlow 절차대로 Runtime 전체를 새로 만들며 공유 Data는 유지한다.
- Editor의 Domain Reload 설정 차이, Play 재진입, 앱 종료, 테스트 간 정적 참조 초기화를 검증한다. 테스트 전용 정리와 제품의 한 판 재시작을 혼동하지 않는다.

### 저장 호환성과 데이터 변경

- 저장 DTO의 정의 ID·개별 ID·관계·생성 순서를 유지한다. Codec의 정의 목록과 참조 동일성 검사를 결합 Data 기준으로 전환하며, 같은 카탈로그의 정규 객체를 사용한다.
- 신규 저장에는 스키마 버전과 게임 값·정의 관계의 정규화 해시를 기록한다. CSV 행 순서·인용 방식·표시 문구·에셋 외형 변경과 실제 게임 규칙/수치 변경을 구분한다. 전체 원본 묶음 해시와 저장 호환성 해시는 목적을 나눈다.
- 기본 정책은 보수적으로 둔다. 진행에 영향을 주는 수치·크기·정의 관계가 달라지면 기존 저장을 새 값으로 조용히 재해석하지 않고 호환 오류를 표시한다. 원본 저장을 보존하고 자동 저장·자동 신규 시작을 차단한다. 올바른 데이터로 재시도하거나 사용자가 명시적으로 새 게임을 선택할 수 있게 한다.
- 이관 전 v1~v4 저장에는 데이터 해시가 없어 생성 당시 밸런스와 출처를 판별할 수 없다. 구버전은 기준 배포 데이터로 작성됐다고 전제하고 현재 카탈로그가 이관 기준 지문과 일치할 때 기존 구조·상태 검증을 거쳐 복원한다. 이 전제가 맞지 않는 저장까지 동일한 밸런스임을 보장하지 않는다. v1은 진단 경로에서만, v2~v4는 플레이 경로에서 기존 지원 범위를 유지한다. 복원 성공 후 다음 정상 저장부터 새 형식과 데이터 지문을 기록하며, 실패 시 원본 파일을 보존한다. 기준 지문과 구버전 fixture를 검증 증거로 남긴다.
- 기존 침공 설정의 한 판 스냅샷·구버전 종료 이관·멸망/결과 단계 복원을 보존한다. 데이터 정비를 이유로 이미 누적된 점수·소비된 재료·생산 진행을 다시 계산하거나 초기화하지 않는다.
- 게임을 새로 실행하면 변경된 CSV로 Data를 다시 로딩한다. 변경된 밸런스는 새 판에 적용한다. 기존 판의 수치 자동 재조정·과거 데이터 버전 다운로드/보관은 이번 범위에 넣지 않는다.
- 데이터 실패·저장 호환 오류·복원 실패를 구분한다. 재시도와 명시적 새 게임도 기존의 저장 성공 후 세션 공개·실패 시 보존 절차를 지킨다.
