# 검증과 완료 판정 지침

PLAN 작업은 현재 `active` PLAN의 타입·완료 조건에 맞춰 검증을 선택하고 실제 결과를 기록한다.
PLAN 상태와 전환은 [작업 절차](workflow.md)를 따른다.
[독립 Sprite 작업](art-assets.md#sprite-requests)은 요청 규격과 변경 영향에 맞춰 검증하고 결과·증거를 요청 README에 기록한다.

## 변경에 맞는 검증 선택

| 수준 | 주요 대상 | 확인 예 |
| --- | --- | --- |
| 문서·정적 확인 | 지침·계획·참조 및 코드 구조 | 링크·줄 수·PLAN 상태·변경 범위·컴파일 |
| 로직 검증: Edit Mode 중심 | 일반 C# Thing·컴포넌트·공통 시스템 | 규칙 결과, 상태 독립성, 소유·예약, 저장·복원 |
| Unity 통합: Play Mode 중심 | 씬·프리팹·SO 연결·화면 입력 | 누락 참조, 공통 명령 전달, 화면과 논리 상태의 일치 |
| Android 빌드 | 대상 플랫폼 패키징·설정 | 빌드 성공, 실제 산출물, 빌드 오류 |
| Android 실기기 | 실행·표시·터치·방향 전환·성능 | 기기에서 기본 흐름 실행, 가로·세로 조작과 상태 유지 |

- 모든 수정에 모든 수준을 실행하지 않는다. 변경의 영향과 PLAN 완료 조건에 필요한 검증을 고른다.
- 컴파일 성공·테스트 통과·빌드 성공·기기 실행 확인은 각각 구분한다.
- 단순 문서 수정에는 링크·줄 수·상태 일관성 검사를 사용한다. 게임 테스트를 불필요하게 추가하지 않는다.
- 새로운 변경·실패·남은 우려가 없다면 같은 검증을 반복하거나 범위를 계속 늘리지 않는다.
- 테스트 도구·명령은 실제 프로젝트와 패키지에서 확인한다. [Unity 도구 지침](unity-tools.md)의 검증된 절차를 사용한다.
- 씬 초기화·전환·Editor 직접 실행 변경은 [씬 흐름 지침](scene-flow.md)의 검증 항목을 함께 확인한다.
- 객체 소유·수명·싱글톤·static 공유 상태 변경은 [객체 설계의 검증 기준](object-design.md#verification)에 따라 독립성·초기화·정리·반복 실행을 확인한다.
- 초기 추상화 도입·기존 코드 공통화는 [추상화의 효과·검증 기준](abstraction.md#verification)에 따라 계약·실제 연결·동작 보존과 변경 작업 감소를 확인한다.
- 문구·번역·언어 변경은 [Localization 검증 기준](localization.md)의 원본/테이블·검토 추적·표시 수명 검사를 함께 적용한다.

<a id="art-plan-test-readiness"></a>

## 아트 PLAN의 테스트 시작 조건

- `type: art` PLAN은 **해당 PLAN에 포함된 모든 필수 리소스의 제작·수령·적용과 참조 연결이 끝난 뒤에만 테스트를 시작한다.** 2026-11-07 사용자 지시이며 현재 진행 중인 PLAN에도 이후 작업부터 적용한다.
- 미제작·미수령·미적용 리소스가 하나라도 남으면 Edit Mode·Play Mode, 수동 게임 실행·검수용 화면 캡처, 회귀·성능·빌드·실기기 테스트를 진행하지 않는다. 개별 리소스를 적용할 때마다 부분 테스트를 반복하지 않는다.
- 준비 중에는 리소스 제작·수령·슬라이싱·임포트·참조 연결과 이에 수반되는 필수 Editor 처리, 파일·설정·참조의 정적 확인 및 문서 검사를 진행할 수 있다. 이를 게임 테스트 통과로 기록하지 않는다.
- PLAN과 요청 README에 리소스별 작업 상태와 남은 항목을 기록하고, 전체 적용 완료를 확인한 뒤 계획한 검증을 수행한다. 임시 대체본으로 미완료 항목을 채우거나 일부 항목을 독립 요청으로 분리해 시작 조건을 우회하지 않는다.
- 전체 리소스 적용 완료와 테스트 통과·사용자 최종 시각 확인은 별도 단계다. 리소스가 준비됐다는 이유만으로 PLAN을 완료 처리하지 않으며, 빌드는 아래 별도 승인 조건도 충족해야 한다.
- 이미 수행한 부분 테스트와 증거는 당시 이력으로 보존한다. 미완료 리소스가 남은 동안 추가 테스트는 대기로 기록하며, 다른 PLAN의 리소스까지 기다리는 조건으로 확대하지 않는다.

<a id="build-test-authorization"></a>

## 빌드 테스트 실행 조건

- 빌드 테스트는 사용자가 빌드 자체를 명시적으로 요청하거나 승인한 경우에만 실행한다. 일반적인 구현 요청이나 PLAN 실행 승인만으로 빌드 테스트가 허용됐다고 간주하지 않는다. 같은 범위에 대해 이미 받은 빌드 요청·승인은 유지하며 반복 확인하지 않는다.
- 빌드 테스트에는 APK/AAB·PC Player 생성, Player 스크립트 컴파일, IL2CPP 검증을 포함한다. 명령·메뉴·하네스가 내부적으로 이 작업을 호출하는 경우에도 같은 조건을 적용한다.
- 기본 검증은 변경 영향에 따라 정적 검사·Editor 임포트/스크립트 재컴파일·Edit Mode·Editor Play Mode 중 필요한 범위를 선택한다.
- 사용자 요청이 없는 빌드 테스트는 PLAN의 기본 검증 범위와 필수 완료 조건에서 제외한다. 미실행과 그에 따른 플랫폼 검증 한계는 기록하고, 빌드 성공이나 기기 동작을 확인한 것으로 표현하지 않는다.

<a id="load-test-authorization"></a>

## 고부하 테스트 실행 조건

- 고부하 테스트는 사용자가 고부하 테스트 자체를 명시적으로 요청하거나 승인한 경우에만 실행한다. 2026-11-12 사용자 지시이며 진행 중·보류 중인 PLAN의 이후 작업에도 적용한다.
- 고부하 테스트는 성능·처리량·한계를 확인하려고 개체 수·데이터량·동시 작업을 의도적으로 늘리는 부하/스트레스 시나리오와 그 반복 계측을 뜻한다. 이를 위한 예비 검사·전후 비교·추가 진단·재실행도 같은 조건을 따른다. Editor·하네스·자동 테스트에 포함됐다는 이유로 예외를 두지 않는다.
- 일반적인 구현·검증·PLAN 실행/재개 요청이나 PLAN에 적힌 측정 계획은 고부하 테스트 승인으로 간주하지 않는다. 같은 범위의 명시적 요청·승인은 유지하되 사용자 중단·철회 이후에는 다시 요청받기 전까지 재실행하지 않는다.
- 요청받은 경우 대상 부하·반복 횟수·예상 실행 시간과 요청 근거를 PLAN 또는 독립 작업 기록에 남기고 그 범위만 실행한다. 일반 회귀와 함께 실행할 때도 승인받지 않은 고부하 시나리오는 필터로 제외한다.
- 사용자 요청이 없는 고부하 테스트는 기본 검증과 필수 완료 조건에서 제외한다. 미측정 범위·한계를 기록하고 통과나 성능 무회귀로 표현하지 않는다. 이미 발견한 실패·비용 증가·과거 증거는 보존하며 미실행과 구분한다.
- 변경에 필요한 일반 기능·저장/복원·입력·수명 회귀는 계속 선택할 수 있다. 단순히 테스트 실행 시간이 길다는 이유만으로 모두 고부하로 분류하거나, 고부하 계측을 기능 회귀로 이름만 바꿔 실행하지 않는다.

## 로직과 하네스

- [하네스 지침](harness.md)에 따라 UI와 같은 명령·규칙·상태를 검증한다.
- 승인된 기획과 관찰 가능한 결과를 기준으로 테스트한다. 구현을 그대로 복사한 기대값을 사용하지 않는다.
- 변경과 관련된 정상 흐름, 중요한 예외, 저장·복원 후 관계를 확인한다.
- 기능 추가 시 해당 상태의 저장·복원과 초기화도 함께 검토한다.
- 아직 구현하지 않은 기능은 통과로 표시하지 않는다. 현재 PLAN의 범위와 후속 범위를 구분한다.
- 테스트를 완화하거나 비활성화해 통과시켰다면 원인 해결로 보고하지 않는다.

## 결과 확인

1. 실행 환경과 대상 테스트·시나리오를 확인한다.
2. 실제 명령 또는 도구 호출과 실행 대상을 기록한다.
3. 프로세스 종료 결과, 테스트 결과 파일·실행 수·실패·건너뜀, 관련 로그를 함께 확인한다.
4. 실행 대상이 발견되지 않아 테스트가 0개인 경우 검증 통과로 처리하지 않는다.
5. 해당 실행에서 생성된 결과인지 확인한다. 이전 실행의 로그·산출물을 새 증거로 사용하지 않는다.
6. 오류가 있으면 원인과 영향을 정리하고, 수정 후 필요한 범위만 다시 검증한다.

도구 호출 성공이나 종료 코드만으로 모든 테스트가 실행됐다고 판단하지 않는다.
Editor·CLI·MCP 연결 성공도 게임 로직 검증 성공과 구분한다.

## Android와 화면 검증

- 승인된 플랫폼과 검증 범위는 [플레이 환경](../game-design/04-delivery/01-platform/environment.md)을 따른다.
- PC Play Mode나 Android 빌드만으로 실기기 터치·성능이 확인됐다고 기록하지 않는다.
- 아트는 [아트 지침](art-assets.md)에 따라 에이전트의 임포트·참조 기술 검증과 사용자의 최종 시각 검수를 구분해 기록한다.
- 가로 기본 사이클을 먼저 구현하고 세로 대응을 추가하는 [구현 순서](../game-design/05-development/02-implementation/roadmap.md)를 유지한다.
- 최종 기기 검증에는 두 방향의 표시·입력·전환을 포함한다. 조작 중 상태 변화도 확인한다.
- 엔진·패키지·그래픽 설정 변경 시 해당 변경의 실제 영향에 맞춰 기기 검증 범위를 정한다.
- 기기 모델·OS·빌드 식별 정보·방향·실행 조건을 기록한다. 성능 수치는 실제 측정값과 조건을 함께 남긴다.
- 검증 기종·반복 횟수·성능 기준 등의 위임 사항은 작업에 필요한 시점에 정한다.

## PLAN 증거와 완료

현재 PLAN의 검증 결과에는 다음을 남긴다.

| 항목 | 내용 |
| --- | --- |
| 환경·대상 | 사용 버전, 플랫폼·기기, 코드·설정 또는 산출물 식별 정보 |
| 방법 | 재실행 가능한 명령·절차와 테스트·시나리오 이름 |
| 결과 | 실제 실행 수·통과·실패·건너뜀과 관찰 내용 |
| 증거 | 해당 실행의 결과 파일·로그·필요한 화면·빌드 산출물 위치 |
| 미검증·문제 | 실행하지 못한 항목, 이유, 영향, 다음 행동 |

- 요구한 검증을 실행할 수 없다면 가능한 확인까지 마치고 제한과 재개 조건을 기록한다.
- 미실행·건너뜀을 통과로 표시하지 않으며, [타입별 완료 규칙](../plans/AGETNS.md)에 따른 필수 완료 기준이 남으면 PLAN을 `completed`로 바꾸지 않는다.
- 문서 작성 완료·설계 승인·설치 완료와 실제 구현·검증 완료를 구분한다.
- 로드맵에는 단계 요약과 PLAN 링크를 남기고 상세 실행 기록은 PLAN에서 관리한다.
- 장기 기술 선택은 [기술 결정](../decisions/README.md), 최종 제품 판정은 [프로토타입 완료 기준](../game-design/04-delivery/02-release/scope.md)을 따른다.
