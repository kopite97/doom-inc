# 추상화·재사용 판단 기준

적용: 기능의 초기 설계·구현, 기존 코드 변경·공통화, 재사용할 데이터 구성·UI·개발 도구를 설계할 때.
탐색: [아키텍처](architecture.md), [객체 설계](object-design.md), [스크립트 구조](script-structure.md), [검증](verification.md), [PLAN 관리](../plans/AGETNS.md).

## 목적과 적용 범위

- 추상화는 기능 추가·변경·검증에 드는 작업을 줄이기 위해 도입한다. 코드 줄 수나 클래스 수 감소만으로 효과를 판단하지 않는다.
- 초기 구현과 기존 코드 변경 모두에서 검토한다. 구현체·사용처가 하나라는 이유만으로 배제하거나, 일정 횟수 이상 반복되었다는 이유만으로 도입하지 않는다.
- 공통으로 유지할 책임과 독립적으로 달라지는 부분을 나눈다. 이름·필드·반복문의 모양보다 의미와 변경 이유가 같은지 확인한다.
- 객체 형태·Unity 의존성·소유와 수명·싱글톤 여부는 [객체 설계](object-design.md)에서 별도로 판단한다. 추상화가 공유 상태나 전역 접근을 요구하지는 않는다.
- 승인된 게임 규칙과 현재 PLAN 범위를 유지한다. 이 지침 추가만으로 기존 코드를 일괄 개편하거나 미래 기능을 구현하지 않는다.

## 도입 근거

| 근거 | 확인할 증거 |
| --- | --- |
| 반복 수정 | 같은 규칙을 여러 곳에서 함께 수정하거나 수정 누락이 발생한 사례 |
| 확인된 교체 요구 | 승인된 데이터 공급원·저장 방식 등의 교체 요구와 유지할 계약 |
| 공통 사용 | 여러 사용처가 동일한 의미의 처리·검사를 요구하며 함께 바뀌어야 하는 이유 |
| 외부 의존성 격리 | 파일·네트워크·Unity 연결의 세부 사항이 호출부로 퍼지는 위치와 분리할 책임 |
| 독립 검증 | 외부 환경 없이 확인할 핵심 동작과 대체해야 할 의존성 |

- 적어도 하나의 구체적인 근거와 줄어들 작업을 설명할 수 있어야 한다. 가능성만 있는 확장이나 추상화 자체를 위한 가상 구현체는 근거로 삼지 않는다.
- 테스트가 필요하다는 이유로 모든 클래스에 인터페이스를 만들지 않는다. 값 전달·구체 객체·작은 함수만으로 독립 검증이 가능한지 먼저 확인한다.
- 반복 제작의 문제라면 런타임 구조뿐 아니라 프리팹·템플릿·에디터 도구로 해결할 수 있는지도 검토한다.

## 초기 기능 구현의 판단

| 판단 | 조건 | 구현 방향 |
| --- | --- | --- |
| 지금 추상화 | 교체·공통 사용·외부 격리·검증 근거와 유지할 계약이 명확함 | 필요한 경계와 최소 계약을 정의하고 현재 필요한 구현만 작성 |
| 책임만 분리 | 독립 책임은 명확하지만 변화 방식이나 공통 계약은 불확실함 | 구체 클래스로 분리하고 필요한 의존성을 전달 |
| 구체 구현 유지 | 단일 기능이며 별도 변화·재사용·격리의 근거가 없음 | 해당 기능 안에서 단순하게 구현하고 근거가 생기면 재평가 |

1. 현재 요구와 승인된 확장 요구를 확인하고 추측과 구분한다.
2. 독립적으로 달라질 부분과 구체적인 변경 사례를 정한다.
3. 변경 후에도 유지할 입력·결과·실패·상태 소유 등 계약을 확인한다.
4. 지금 분리하지 않을 때 세부 구현이 여러 호출부로 퍼지는지, 나중에 한곳에서 쉽게 분리할 수 있는지 비교한다.
5. 아래 수단 중 가장 작은 것으로 시작한다. 계약이 불확실하면 대표 기능 하나를 처음부터 끝까지 연결해 확인한 뒤 공통 범위를 확장한다.

책임 분리와 인터페이스 도입은 별도 결정이다. 구체 클래스와 명시적인 의존성 전달만으로 충분하면 그 상태를 유지한다.

## 수단 선택

| 상황 | 우선 검토할 수단 |
| --- | --- |
| 같은 계산·변환·검사 규칙 | 작은 함수 또는 책임이 명확한 클래스 |
| 수치·문구·에셋 등 정의만 다름 | JSON·SO 등 데이터 구성과 공통 처리. [정의 데이터 기준](../game-design/05-development/01-architecture/thing-model.md) 준수 |
| 외부 공급원·처리 방식 교체 | 좁은 인터페이스와 구현체·어댑터 |
| 여러 기능에서 일부 동작 공유 | 별도 객체를 연결하는 조합 방식 |
| 공통 절차와 불변 조건이 확실함 | 조합과 비교한 뒤 필요한 경우 추상 기반 클래스 |
| 동일한 연산을 여러 타입에 적용 | 타입 안전성과 계약이 명확한 경우 제네릭 |
| 화면·에셋 구성·제작 절차 반복 | 재사용 UI 구성·프리팹·템플릿·에디터 도구 |
| 모양은 비슷하지만 규칙·변경 이유가 다름 | 독립 구현 유지 |

- 인터페이스·상속·제네릭·DI 프레임워크를 기본 묶음으로 도입하지 않는다. 작은 추상화에 불필요한 계층을 추가하지 않는다.
- 데이터로 표현할 수 있는 정의 차이마다 하위 클래스를 만들지 않는다. 반대로 서로 다른 행동을 무리하게 옵션 데이터로 표현하지 않는다.
- 상속을 쓰면 모든 하위 구현이 공통 계약과 불변 조건을 지킬 수 있어야 한다. 일부 기능을 사용하지 못하는 빈 재정의로 공통화를 유지하지 않는다.

## 기존 코드의 공통화와 재평가

- 실제 호출부·중복 규칙·변경 사례를 먼저 조사한다. 같은 의미의 규칙이 한곳에서 관리되도록 하되 서로 다른 규칙을 억지로 합치지 않는다.
- 기존 동작을 보존하는 추출과 게임 규칙 변경을 구분한다. 승인된 작업 범위 안에서 작은 단위로 적용하고 영향받는 호출부를 함께 확인한다.
- 공통 계약의 입력·결과와 관련된 실패·취소·초기화·정리 책임을 정의한다. 수명 세부 기준은 [객체 설계](object-design.md)를 따른다.
- 호출부가 구현체 종류를 검사하거나 구체 타입으로 변환해야 사용 가능한지 확인한다. 반복되는 특수 처리는 계약 분리·조합 또는 공통화 철회의 근거로 삼는다.
- 특정 기능 전용 플래그·분기·가상 메서드가 계속 늘거나, 한 기능 수정이 무관한 기능에 영향을 주면 공통 범위를 재검토한다.
- 공통 코드에도 책임이 드러나는 이름과 위치를 사용한다. [프로젝트 구조](project-structure.md)와 [명명 규칙](naming.md)을 따르며 무관한 기능을 유틸리티 모음으로 옮기지 않는다.

## 프로젝트 적용 예

아래는 판단 예이며 새 기능 구현 지시가 아니다.

| 사례 | 판단 |
| --- | --- |
| IGameDataSource | 로컬 JSON 이후 원격 공급원으로 교체하는 요구가 있으므로 취득 계약을 분리한다. 원격 구현은 해당 작업 범위에서 추가한다. |
| 시설 정의의 시간·투입량·산출물 차이 | 우선 데이터와 공통 처리로 표현한다. 행동 규칙이 다른 경우 별도 판단한다. |
| 공용 LoadingScreen | 공통 표시 책임을 재사용한다. 단일 화면 구현에 인터페이스나 별도 싱글톤을 자동 추가하지 않는다. |
| 생산·운반·건설 Manager | 이름이나 갱신 구조의 유사성만으로 공통 기반 클래스를 만들지 않는다. 실제 같은 규칙이 확인된 부분부터 분리한다. |

## 효과 확인·검증·기록

- 같은 규칙의 수정 위치, 새 구현 추가 시 기존 호출부 변경량, 동작을 이해하기 위해 따라갈 단계, 검증 준비 작업을 비교한다.
- 초기 구현은 대표 사용 흐름에서 계약과 실제 연결을 확인한다. 추상화 효과를 입증하려고 미요구 제품 구현체를 추가하지 않는다.
- 기존 코드 추출은 관찰 가능한 결과·상태 변화·관련 실패 동작이 유지되는지 확인한다. 테스트가 내부 클래스 분할 자체를 정답으로 고정하지 않게 한다.
- 대체 구현이 있으면 공통 계약을 지키는지 확인하고, 외부 의존성을 테스트 대역으로 바꿨다면 실제 구현과 연결되는 경계도 영향에 맞게 검증한다.
- 검증 수준과 빌드 실행 조건은 [검증 지침](verification.md)을 따른다. 생산성 개선을 실행 성능 개선으로 단정하지 않는다.
- 설계 선택은 기존 PLAN에 `근거 / 공통 책임 / 달라지는 부분 / 선택한 수단·대안 / 적용 범위 / 줄어들 작업 / 검증`을 변경 규모에 맞춰 기록한다.
- 작은 함수 추출마다 별도 문서나 승인을 요구하지 않는다. 영향이 큰 선택은 [기술 결정](../decisions/README.md)에 남기며, 근거가 달라지면 선택도 재평가한다.
