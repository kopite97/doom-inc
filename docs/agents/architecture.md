# 아키텍처 변경 지침

적용: 정의·Thing·컴포넌트·Job·Map·저장·GameFlow·화면 연결을 설계하거나 변경할 때.
탐색: [작업 절차](workflow.md), [하네스](harness.md), [검증](verification.md).

## 기준 읽기

1. active PLAN의 변경 범위와 [로드맵](../game-design/05-development/02-implementation/roadmap.md)의 단계 기준을 확인한다.
2. [Thing과 정의 데이터](../game-design/05-development/01-architecture/thing-model.md)를 읽는다.
3. 단계 전환·시작·복원 작업이면 [GameFlow](../game-design/05-development/01-architecture/game-flow.md)를 읽는다.
4. 생산·운반·공간 등 상세 규칙은 [기획 MAP](../game-design/README.md)의 담당 문서에서 확인한다.
5. 코드 위치·기능별 분류는 [스크립트 구조](script-structure.md)를 따른다. 폴더 분류를 상태 소유나 어셈블리 분할과 혼동하지 않는다.
6. 클래스 역할·Manager 책임과 이름은 [명명 규칙](naming.md)을 함께 확인한다.

이 문서는 변경 시 확인할 경계를 안내한다. 게임 수치·예약 예외·레시피의 원본을 복제하지 않는다.

## 변경별 확인 사항

| 변경 대상 | 구현과 검증에서 확인할 경계 |
| --- | --- |
| SO 정의 | 공통 정의와 실행 상태를 구분하고, 플레이 중 공유 정의를 상태 저장소로 쓰지 않는다. |
| Thing·컴포넌트 | 일반 C# 객체의 개별 상태와 소유 관계를 유지하며 화면 표현과 분리한다. |
| Job·생산 | 개체의 행동과 시설에 남는 생산 회차 상태를 구분한다. |
| 자원·예약 | 실물의 단일 보관처와 출고·입고 예약을 구분한다. |
| Map·배치·경로 | 같은 공간 정보를 참조하고 배치 가능과 접근 가능을 구분한다. |
| 외부 활동 | Map에서 제외된 개체의 존재·성과 상태를 유지한다. |
| 저장·복원 | 고유 ID·관계·최초 생성 순서와 현재 구현 범위의 상태가 이어지는지 확인한다. |
| GameFlow | 한 판의 전환과 각 담당 시스템의 상태 소유를 구분한다. |
| UI·하네스 | 같은 명령 처리·규칙 검사·상태 조회를 거친다. |

각 경계의 세부 의미와 예외는 기준 기획을 따른다. 표의 행마다 클래스나 Manager를 만들라는 뜻이 아니다.
Unity의 MonoBehaviour와 게임 실행 컴포넌트는 서로 다른 역할이다.

## 구현 선택

- 현재 PLAN과 단계에 필요한 최소 구조를 설계한다. 림월드 전체 구조나 출시용 프레임워크를 먼저 만들지 않는다.
- 일반 C# 실행 객체 선택을 DOTS/ECS 도입이나 모든 Unity 타입 제거 요구로 바꾸지 않는다.
- 정확한 클래스·컴포넌트 분할·조회 API·알고리즘·갱신 순서는 개발 위임 범위에서 결정한다.
- 기존 상태를 다른 객체에 다시 저장해 두 원본이 생기지 않도록 상태 소유자를 명확히 한다.
- 실행 코드에 Editor 전용 의존성을 섞지 않는다. Unity 연결은 필요한 경계에서 처리한다.
- 다른 시스템에 영향이 큰 선택은 [기술 결정](../decisions/README.md)에 이유·대안·적용 위치를 남긴다.

## 검증과 기록

- 변경된 경계의 정상 흐름과 관련 예외를 [하네스](harness.md)·[검증](verification.md) 지침으로 확인한다.
- 진행 상태나 연결 관계를 추가하면 해당 구현 단계에서 저장·복원 검증도 확장한다.
- 상태 독립성·자원 소유·예약·복원처럼 깨지면 게임 사이클에 영향을 주는 조건을 우선 검증한다.
- 검증 범위를 넘어선 기능을 미리 구현하지 않는다. 다음 단계의 상태는 해당 단계에서 추가한다.
- 적용한 결정과 실제 검증은 active PLAN에 연결하며 기획 규칙 변경과 구분한다.
