# 씬 책임·전환·직접 실행 지침

적용: 씬별 책임, 앱 초기화, 씬 전환, 세션 진입·정리, Editor 직접 실행과 관련 검증을 설계하거나 변경할 때.
탐색: [아키텍처](architecture.md), [GameFlow 기준](../game-design/05-development/01-architecture/game-flow.md), [하네스](harness.md), [Unity 에셋](unity-assets.md).

이 문서는 사용자가 승인한 구현 원칙이다. Bootstrap·Title·Laboratory와 공용 LoadingScreen의 실제 구현·검증 범위는 [PLAN-016](../plans/PLAN-016-bootstrap-title-and-scene-flow.md), 공통 구성과 수명 선택은 [TECH-013](../decisions/TECH-013-app-scenes-and-loading-screen.md)에서 관리한다.
씬 경로·제품/검증 의존 관계·빌드 포함 기준은 [프로젝트 구조](project-structure.md#scene-roles)를 따른다. 저장 정책·게임 규칙은 [기획 MAP](../game-design/README.md)의 담당 문서가 기준이며, 새 정책은 기획에 반영한다.

## 씬별 책임

| 씬 | 책임 | 준비 완료·종료 경계 |
| --- | --- | --- |
| Bootstrap | 앱 최초 진입, 공통 초기화 요청, 로딩·오류·재시도 표시 | 공통 데이터 준비 성공 후 Title 진입을 요청한다. 플레이 세션을 자동 생성하지 않는다. |
| Title | 저장 상태에 따른 새 게임·이어하기·설정 UI와 시작 요청 | 시작 방식과 저장 슬롯을 명시해 Laboratory 진입을 요청한다. 시뮬레이션과 플레이 자동 저장을 실행하지 않는다. |
| Laboratory | 전달받은 시작 요청으로 세션 생성·복원, 플레이·멸망 연출·결과 표시 | 데이터와 세션 준비 후 조작을 허용한다. 재시작·메뉴 복귀 시 기존 세션의 종료 처리를 요청한다. |

- 제품 시작 흐름은 Bootstrap → Title → Laboratory로 구성한다. 메뉴 복귀는 Title로 이동하며 공통 데이터를 다시 로드하지 않는다.
- 멸망 연출·결과·새 판 시작은 Laboratory 안에서 기존 GameFlow 경로로 처리한다. 설정·일시정지·확인 UI와 로딩 표시를 이유로 별도 씬을 늘리지 않는다.
- 이어하기는 저장된 진행 단계로 복원한다. 새 게임·이어하기·재시작을 암묵적인 저장 유무 분기 하나로 합치지 않는다.
- 저장 없음·복원 실패·새 게임의 기존 저장 처리·메뉴 복귀 시 저장 성공/실패를 구분해 UI와 전환 계약에 반영한다. 실패를 새 판 시작이나 저장 삭제로 조용히 바꾸지 않는다.

## 단일 씬 전환 관리자

- SceneFlowManager 한 클래스가 씬 전환을 담당한다. 씬 간 유지되는 싱글톤 MonoBehaviour로 두고 중복 인스턴스를 방지한다.
- 이는 사용자 승인에 따른 [Manager 기본 원칙](naming.md)의 한정된 예외다. 다른 게임 Manager까지 싱글톤으로 바꾸지 않는다.
- 제품 UI·씬 진입점·디버깅 도구는 공통 전환 요청을 사용한다. 각자 별도의 제품 씬 전환 로직을 만들지 않는다. 테스트의 초기 씬 로드·정리는 테스트 준비로 구분한다.
- 관리자는 전환 요청, 중복 차단, 입력 잠금, 로딩 표시, 기존 세션 정리 요청, 씬 로드와 대상 준비 완료, 실패 복구 순서를 조율한다.
- JSON 파싱·SO 결합·저장 직렬화·생산 계산은 각 담당 기능에 위임한다. 일반 C# 게임 로직에서 Unity 씬 관리자에 전역 접근하도록 연결하지 않는다.
- GameFlowManager는 한 판의 단계·생성·복원·재시작을 계속 담당한다. SceneFlowManager가 이를 요청하되 진행 상태를 중복 소유하지 않는다.
- 시작 요청에는 대상·새 게임/이어하기 구분·저장 슬롯 등 필요한 맥락을 명시한다. 이전 요청이 다음 진입에 재사용되거나 같은 요청이 두 번 소비되지 않게 한다.
- 전환은 한 번에 하나만 수행한다. 대상 씬의 로드 완료와 사용 가능한 데이터·세션의 준비 완료를 구분하고, 모두 준비된 뒤 입력을 허용한다.
- 전환 중 실패하면 현재 단계와 원인을 표시하고 재시도 또는 안전한 화면 복귀 경로를 제공한다. 전환 잠금이 영구 유지되거나 실패한 요청이 뒤늦게 완료되지 않게 한다.

## 공통 초기화와 수명

- 공통 초기화를 Bootstrap 씬의 존재와 분리해 호출할 수 있게 한다. Bootstrap은 해당 기능의 제품 시작 진입점이며, Editor 직접 실행도 같은 기능을 호출한다.
- 같은 데이터 구성의 초기화가 완료됐으면 재사용하고, 진행 중이면 동일 작업을 기다린다. 실패 시 명시적으로 재시도하며 부분적으로 준비된 데이터를 공개하지 않는다.
- JSON 데이터 소스·SO Registry·결합·검증 설정은 하나의 정규 구성에서 공급한다. 직접 실행용 정의와 Registry 목록을 씬마다 복제하지 않는다.
- GameDataStore와 SceneFlowManager는 앱 수명, 한 판의 실행 상태는 세션 수명, 화면·입력 연결은 씬 수명으로 구분한다. 영구 객체에 파괴된 씬 참조를 남기지 않는다.
- 데이터 준비 실패 시 세션 생성·진행·자동 저장을 시작하지 않는다. Title·Laboratory 직접 진입에서도 동일하게 적용한다.
- 씬을 떠나거나 세션을 교체할 때 저장 정책에 따른 처리를 마친 뒤 시뮬레이션·자동 저장·이벤트 구독·입력·씬 소유 비동기 작업을 정리한다. 저장 실패를 성공으로 처리하지 않는다.
- 취소 가능한 작업은 수명 종료 시 취소하고, 취소할 수 없는 작업은 늦게 도착한 결과가 떠난 씬이나 새 세션을 수정하지 못하도록 무효화한다. 공유 초기화의 수명은 개별 씬과 구분한다.
- 앱 일시정지·포커스 복귀 중에도 기존 진행 정지 규칙을 유지하고, 전환·입력 이벤트가 중복 적용되지 않게 한다.

## Editor에서 각 씬으로 직접 진입

| 실행 선택 | 준비와 진입 |
| --- | --- |
| 전체 시작 흐름 | Bootstrap → Title → Laboratory의 제품 진입 경로를 검증한다. |
| 현재 Title 씬 | 공통 초기화 완료를 보장한 뒤 Title을 사용 가능하게 한다. |
| 현재 Laboratory 씬 | 공통 초기화 후 선택한 테스트 시작 요청으로 세션을 생성·복원한다. |
| Diagnostics 씬 | 해당 검증 시나리오의 준비와 공통 초기화·명령 경로를 사용한다. |

- Editor에서 현재 씬 실행과 전체 시작 흐름 실행을 선택할 수 있게 한다. 직접 실행 때문에 Bootstrap·Title 화면을 매번 거치게 하지 않는다.
- 직접 실행은 필요한 영구 객체와 의존성 준비를 보장한다. 대상 씬의 자동 시작과 도구의 시작 요청이 경쟁해 세션이 두 개 생성되지 않게 한다.
- 실행 설정은 진입 위치, 새 테스트 판/테스트 저장 이어하기, 필요한 초기 상태 시나리오를 명시한다. 선택하지 않은 테스트 상태를 자동 주입하지 않는다.
- 초기 상태 준비는 [하네스의 시나리오·상태 준비 규칙](harness.md)을 따른다. 준비용 주입과 실제 사용자 명령 검증을 구분하고 게임 규칙을 복제하지 않는다.
- 테스트 저장 슬롯은 제품 저장과 분리한다. Editor 전체 흐름 검증에도 격리된 슬롯을 전달해 제품 저장을 읽거나 덮어쓰지 않는다.
- 실행 설정·시나리오 선택·자동 진입 도구는 Editor 전용으로 격리하고 제품 빌드에 포함하지 않는다. 제품 초기화 기능에는 Editor 의존성을 추가하지 않는다.
- 도구가 Editor 시작 씬 등 설정을 임시 변경하면 종료·실패 시 복원한다. 실행을 위해 제품 씬의 직렬화 구성이나 빌드 씬 목록을 임시 수정하지 않는다.
- Play Mode 재진입과 Domain Reload 비활성에서도 이전 싱글톤 참조·정적 이벤트·진입 요청·비동기 결과가 남지 않도록 초기화한다. 일반 씬 전환 중에는 준비된 공통 데이터를 유지한다.

현재 도구는 `Tools/Mobile Game/Play`의 Current Scene 새 판/이어하기·Full Bootstrap Flow·Default/Alternate Test Slot을 사용한다. Prepare Operating/Near Ending Test Save는 공통 명령과 시간 진행으로 선택한 Editor 슬롯을 준비한다. 제품 저장과 분리하며 준비 완료 후에만 슬롯을 교체한다. 준비 데이터는 사용자 입력 검증 결과로 집계하지 않는다.

## 구현 시 검증

- 전체 시작 흐름과 Title·Laboratory 직접 실행을 각각 확인한다. 직접 실행 성공만으로 제품 시작 흐름을 검증했다고 기록하지 않는다.
- 중복 초기화·전환 요청, 데이터 로딩 실패와 재시도, 저장 없음·복원 실패, 메뉴 복귀·재진입·새 판 시작을 변경 범위에 맞게 검증한다.
- 영구 객체 단일성, 기존 세션의 진행·자동 저장 종료, 이벤트·입력 정리, 늦은 비동기 결과 차단과 테스트 저장 격리를 확인한다.
- Domain Reload 활성/비활성의 Play Mode 재진입과 실제 선택한 Editor 실행 경로를 검증 기록에 남긴다.
- 검증 범위와 완료 판정은 [검증 지침](verification.md)을 따른다. 빌드는 [별도 사용자 요청·승인 조건](verification.md#build-test-authorization)을 따른다.
