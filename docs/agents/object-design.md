# 객체 설계·수명·공유 기준

적용: Manager를 포함한 모든 객체의 형태, Unity 의존성, 소유·수명, 싱글톤·static 사용을 설계하거나 변경할 때.
탐색: [아키텍처](architecture.md), [스크립트 구조](script-structure.md), [명명](naming.md), [씬 흐름](scene-flow.md), [검증](verification.md).

## 판단 순서

| 순서 | 결정할 내용 |
| --- | --- |
| 책임 | 게임 규칙·실행 상태·표시·입력·저장·에셋 구성 중 무엇을 담당하는가? |
| 소유자와 수명 | 누가 생성·초기화·정리하며 앱·세션·씬·개체·일회성 작업 중 어디에 속하는가? |
| 객체 형태 | 일반 class·struct·MonoBehaviour·ScriptableObject 중 어떤 형태가 필요한가? |
| Unity 의존성 | 엔진 의존 없음·값 타입 사용·에셋 참조·엔진 기능 호출 중 어디까지 필요한가? |
| 공유와 접근 | 개별 인스턴스·참조를 전달하는 공유 인스턴스·싱글톤·static 중 무엇이 필요한가? |

- 객체 형태·Unity 의존성·수명·공유 방식은 각각 판단한다. 이름이나 현재 인스턴스 수만으로 결정하지 않는다.
- 초기 구현·기존 코드 변경에서 책임을 공통화하거나 인터페이스·상속·조합을 선택할 때는 [추상화 기준](abstraction.md)을 함께 적용한다.
- 일반 C# 객체는 MonoBehaviour·ScriptableObject를 상속하지 않는 객체를 뜻한다. Unity 의존성이 전혀 없는 코드는 별도로 구분한다.
- Manager도 일반 C# 객체로 두고 의존성을 명시적으로 연결하는 것을 기본으로 한다. 엔진 연결·싱글톤이 필요한 경우 아래 공통 기준으로 판단한다.
- 기존 게임 규칙·데이터 계약은 [기획 MAP](../game-design/README.md)을 따른다. 이 지침 추가만으로 기존 객체를 일괄 개편하지 않는다.

## 객체 형태 선택

| 형태 | 선택 기준 | 제한과 확인 사항 |
| --- | --- | --- |
| 일반 C# class | 식별성·변경 상태가 있는 객체, 게임 규칙, 저장 처리, 서비스의 기본 형태 | 소유자가 생성하고 필요한 참조를 전달한다. Unity 값 타입·에셋 참조 사용 여부는 별도로 판단한다. |
| struct / readonly struct | 좌표·범위·명령 결과처럼 복사해도 의미가 유지되는 작은 값 | 변경 가능한 객체 그래프·복잡한 소유 관계에는 우선 사용하지 않는다. 크기·성능 이점은 추측으로 단정하지 않는다. |
| MonoBehaviour | GameObject에 붙는 동작, Unity 콜백·입력·표시 연결, 코루틴 실행 주체가 필요한 경우 | 게임 계산과 엔진 연결을 분리한다. 매 프레임 진행이 필요하다는 이유만으로 모든 객체에 Update를 두지 않는다. |
| ScriptableObject | GameObject와 독립적인 에셋 참조·구성·Registry를 편집하고 재사용할 경우 | 공유 정의를 플레이 진행 상태의 저장소로 쓰지 않는다. 생성·참조·직렬화는 [Unity 에셋 지침](unity-assets.md)을 따른다. |

- 일반 C# 도우미가 전달받은 Unity 객체를 조작하거나 UI를 구성할 수 있다. 이 경우에도 생성한 객체와 이벤트의 정리 책임을 명시한다.
- Inspector 노출만을 목적으로 게임 규칙 전체를 MonoBehaviour로 옮기지 않는다. 구성 에셋·연결 컴포넌트에서 필요한 값을 전달할 수 있는지 먼저 검토한다.
- 일반 C# 객체의 시간 진행은 소유자가 공통 갱신 경로로 전달할 수 있다. 코루틴·Task 선택과 객체 형태를 동일한 결정으로 취급하지 않는다.

## Unity 의존 범위

| 범위 | 원칙 |
| --- | --- |
| DTO·저장 데이터·규칙 계산 | 엔진 객체나 씬 존재에 의존하지 않는 형태를 우선한다. 저장 연결은 승인된 ID·직렬화 계약을 따른다. |
| 공간·수학 값 | Vector2Int 등 기존 Unity 값 타입을 허용한다. using UnityEngine만으로 MonoBehaviour 상속이나 타입 교체를 요구하지 않는다. |
| 에셋 바인딩 | Sprite·Prefab 등의 참조는 정의·표현 경계에서 관리한다. 필요한 바인딩을 포함한 일반 C# Data도 허용한다. |
| 엔진 기능 | 씬 로딩·입력 취득·오브젝트 생성·표시 갱신은 Unity 연결 책임에서 수행하고 게임 로직에는 필요한 값·명령·의존성을 전달한다. |

- JSON 값 + SO 에셋 참조 → 읽기 전용 Data → 개별 Runtime의 역할은 [정의 데이터 기준](../game-design/05-development/01-architecture/thing-model.md)을 따른다.
- Unity 타입 제거를 목적으로 같은 자료형을 복제하거나 DOTS/ECS·새 프레임워크를 도입하지 않는다.
- Unity API를 호출하는 일반 C# 객체도 해당 API의 실행 스레드·수명 제약을 따른다. Task 사용 자체를 백그라운드 실행이나 스레드 안전성의 근거로 삼지 않는다.

## 소유자와 수명

| 수명 | 소유와 정리 기준 |
| --- | --- |
| 앱 | 공통 초기화가 생성·준비하고 앱 종료·Play 재진입 경계에서 정리한다. 씬 교체와 별도로 수명을 관리한다. |
| 세션 | 한 판의 소유자가 생성하고 새 판·복원·세션 종료 때 교체·정리한다. 다른 판이나 하네스 세션과 변경 상태를 공유하지 않는다. |
| 씬·화면 | 해당 씬·화면 소유자가 연결하고 떠날 때 입력·이벤트·참조를 해제한다. |
| 개체 | Thing 등 소유 개체와 함께 생성·제거하며 같은 종류의 개체끼리 실행 상태가 섞이지 않게 한다. |
| 일회성 작업 | 요청 소유자가 완료·실패·취소를 처리한다. 소유자 종료 뒤 늦게 도착한 결과의 적용을 차단한다. |

- 앱에서 하나를 공유해도 참조 전달만으로 충분하면 일반 공유 인스턴스로 둔다. 앱 수명이 곧 싱글톤을 뜻하지 않는다.
- 영속 객체가 씬·세션 참조를 보관하면 연결·해제 시점을 명시한다. 파괴되거나 교체된 객체의 참조를 다음 사용에 남기지 않는다.
- DontDestroyOnLoad는 씬 교체 시 객체를 유지하는 선택이다. 싱글톤의 중복 방지나 앱 종료 후 파일 저장을 대신하지 않는다.

## 공유 인스턴스·싱글톤·static 판단

새 싱글톤은 다음 항목을 모두 검토하고 선택 이유를 남긴다. 편리한 전역 호출이나 현재 하나만 존재한다는 사실만으로 도입하지 않는다.

1. 단일성이 필요한 범위를 명시한다. 한 판·씬마다 하나인 객체는 해당 소유자가 관리하는 방식을 우선한다.
2. 같은 범위에 둘 이상 존재하면 어떤 책임·상태가 충돌하는지 설명한다.
3. 소유자가 하나를 생성하고 참조를 전달하는 대안과 비교해 싱글톤이 필요한 이유를 설명한다.
4. 전역 접근을 허용할 계층과 호출부를 정한다. 게임 규칙 내부에서 전역 객체를 찾아 의존성을 숨기지 않는다.
5. 생성·준비 전 접근·초기화 실패·재시도·중복·종료·테스트 격리 계약을 정의하고 검증할 수 있어야 한다.

- 싱글톤은 일반 C# 또는 MonoBehaviour로 구현할 수 있다. Unity 연결이 필요한지는 객체 형태 기준으로 별도 판단한다.
- 공용 화면·서비스는 소유자가 재사용하는 방식부터 검토한다. LoadingScreen처럼 소유자가 있는 객체에 별도 Instance를 추가할 필요는 없다.
- 무상태 계산·변환·검사는 static 함수로 둘 수 있다. 입력 외의 변경 가능한 전역 상태를 숨겨 읽거나 쓰지 않는다.
- 변경 가능한 static 필드·정적 이벤트·캐시·static class도 전역 공유 상태로 검토한다. static이라는 이유로 싱글톤의 수명·격리 검토를 생략하지 않는다.
- 초기화 경로가 생성과 의존성 연결을 조율하게 한다. 단순 조회에서 객체 생성·씬 탐색·파일 읽기를 숨겨 수행하지 않는다.
- 공통 Singleton 기반 클래스나 DI 프레임워크는 먼저 만들지 않는다. 실제 반복 책임과 필요한 대체·테스트 경계를 확인한 뒤 도입한다.

## 초기화·종료 계약

- 인스턴스의 존재와 준비 완료를 구분한다. 준비 전 호출은 대기·거절·오류 중 정한 계약으로 처리하며 부분 초기화 상태를 정상 결과로 공개하지 않는다.
- 중복 초기화의 공유·거절 방식을 정하고, 중복 인스턴스 정리가 정상 소유자의 정적 참조·구독·데이터를 제거하지 않게 한다.
- 구독 해제·리소스 해제·취소 요청의 주체를 정한다. 코루틴 중단을 Task나 시작된 씬 로드의 취소 완료로 간주하지 않는다.
- 취소할 수 없는 작업은 요청 식별·세대 검사를 사용해 오래된 결과가 새 소유자·세션에 적용되지 않게 한다.
- Play 재진입 시 정적 참조·이벤트·이전 작업을 초기화한다. Domain Reload 비활성에서도 이전 실행의 변경 상태가 남지 않게 한다.

## 현재 프로젝트의 적용 사례

아래는 공통 판단 기준을 현재 객체에 적용한 사례다. 실제 구현 근거는 [TECH-013](../decisions/TECH-013-app-scenes-and-loading-screen.md)과 관련 PLAN을 따른다.

| 대상 | 적용 기준 |
| --- | --- |
| GameFlowManager·게임 기능 Manager | 일반 C# 객체로 세션이 소유한다. 생산·운반·건설·진행 상태는 판마다 독립적이다. |
| SceneFlowManager | 앱의 씬 전환을 단일 주체가 조율하며 Unity 씬·코루틴 수명과 연결하므로 MonoBehaviour 싱글톤을 사용한다. 상세 책임은 [씬 흐름](scene-flow.md)을 따른다. |
| GameDataStore | 앱 수명으로 정의 카탈로그 준비·공유를 담당한다. 게임 로직에는 필요한 Data를 전달한다. |
| AppUiLifetime | 현재 단일 UI 입력 구성의 앱 수명 소유자다. 개별 Canvas의 수명과 분리한다. |
| LoadingScreen·Title·Laboratory 화면 | 소유자가 연결·재사용·정리한다. 공용 여부만으로 화면 자체를 싱글톤화하지 않는다. |
| SO Registry·AppConfiguration | 에셋 참조와 공통 구성을 담당하며 개별 게임 진행 상태는 소유하지 않는다. |
| AppUiSettings | 현재 변경 가능한 static 공유 상태다. 슬롯·Play 격리와 초기화 계약을 적용하며 상태 없는 유틸리티로 취급하지 않는다. |

## 검증과 기록

- 변경 영향에 따라 상태 독립성, 공유 인스턴스 단일성, 중복 생성·초기화, 준비 실패·재시도, 소유자 종료·늦은 완료를 확인한다.
- 세션·저장 슬롯 교체, 씬 왕복, 직접 진입, 반복 Play에서 참조·구독·변경 상태가 누적되거나 섞이지 않는지 확인한다.
- Unity 수명·정적 공유 상태를 변경하면 Domain Reload 양쪽과 지원하는 Scene Reload 조건을 검증한다. 순수 계산 변경에 이 검증을 일괄 요구하지 않는다.
- 검증 범위와 빌드 실행 조건은 [검증 지침](verification.md)을 따른다. 객체 구조 변경만으로 빌드를 실행하지 않는다.
- 설계 기록은 기존 PLAN의 해당 항목에 `책임 / 객체 형태 / Unity 의존 범위 / 소유자·수명 / 공유·접근 방식 / 초기화·정리 / 선택 이유`를 남긴다.
- 기록의 상세는 변경 규모에 맞춘다. 영향이 큰 선택은 [기술 결정](../decisions/README.md)에 남기며 클래스마다 별도 문서를 만들지 않는다.
