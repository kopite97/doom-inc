# 새 기획의 구현·재사용 지침

적용: 새 기획을 구현하기 위한 기술 설계·재사용·작업 범위 검토.
탐색: [기획 지침](game-design.md), [아키텍처](architecture.md), [추상화](abstraction.md), [밸런스 편집](balance-editor.md).
이 문서는 개발 방법을 다룬다. 게임 규칙의 원본은 [기획 MAP](../game-design/README.md)의 주제 문서다.

## 책임 구분

- 사용자는 1인 개발과 에이전트 활용을 계획한다. 기획은 핵심 경험·규칙을 정하고 상세 기술 설계는 개발하면서 진행한다.
- 클래스·컴포넌트·API·알고리즘·데이터 구조·수치 조정은 확정 규칙 안에서 결정한다. 중요한 선택은 [기술 결정](../decisions/README.md)에 기록한다.
- 승패·손실·명령 수준·플랫폼·콘텐츠 범위의 미정 사항을 기술 선택으로 확정하지 않는다.
- 범위·진행·검증은 PLAN에서 관리한다. 로드맵 작성이 구현 실행 승인이나 완료 증거는 아니다.
- 기획 완료 후의 검토·설계 착수 순서는 [기획 지침](game-design.md#작업-초안과-최종-정리)을 따른다. 범위를 정리한 뒤 공유 상태의 소유·처리 순서·작업 중단 및 예약·저장 복원 경계를 관련 기능 구현 전에 함께 결정한다. 그 경계 안의 세부 클래스·알고리즘·수치는 개발 중 구체화한다.

## 데이터와 재사용

- [시설 상호작용 아이콘](../game-design/experience/interface.md#시설-상호작용-아이콘)은 모든 시설이 공통 표시 기능을 재사용한다. 시설은 가능한 조작과 현재 상태를 제공하고, 공통 기능은 그에 맞는 아이콘과 설명을 시설 위에 표시·갱신한다. 새 시설도 기존 조작·상태를 그대로 연결하며, 플레이어의 선택이나 결과가 달라지는 부분만 개별 기획한다.
- [인게임 대화](../game-design/experience/interface.md#첫-프로토타입의-시작-대화와-첫-지시)와 [첫 플레이 튜토리얼](../game-design/experience/interface.md#첫-플레이-튜토리얼)은 같은 Dialogue 클래스를 재사용한다. 대화 장면마다 대사와 화자, 각 캐릭터 일러스트의 좌우 위치를 지정할 수 있게 한다. 주인공을 오른쪽에 두는 연출은 각 장면의 배치 설정에 반영한다.
- 2026-11-26 사용자 지정: [머리 위 말풍선](../game-design/experience/interface.md#머리-위-말풍선-대사)은 연출형 Dialogue와 별도로 사용할 수 있게 구현하며, 주인공·조수를 포함한 모든 생명체를 지원한다. 일반 생명체의 사용 빈도가 낮아도 지원 대상에서 제외하지 않는다. 표시 방식의 구분만으로 클래스 분리나 공통 데이터 구조를 미리 확정하지 않으며 상세 기술 구조는 해당 기능 개발 때 정한다.
- [생명체](../game-design/systems/creatures.md)의 코스트는 JSON으로 관리한다. 필드·자료형·초기값·검증·호환 방식은 구현 단계에서 정한다.
- 생명체의 작업 특화는 [기획 원칙](../game-design/systems/creatures.md#작업-특화)에 따라 관련 수행 수치를 조정해 표현한다. 특화 여부·종류를 위한 별도 필드나 특화 판정 분기를 추가하지 않는다. 작업 가능 여부와 수행 성능을 혼동하지 않는다.
- 기존 JSON 로딩·밸런스 편집 기반을 활용하며 [밸런스 편집 지침](balance-editor.md)에 따라 실제 동작까지 연결한다.
- 아트·개체·지도·이동·작업·생산·물류·저장·명령·하네스는 재사용 후보이며, 새 규칙과 실제 구현을 대조한다.
- 이전 보조형·침공형 구분, 배정 제한, 전투로 인한 중단·복구와 충돌하는 부분을 확인한다. 전체 교체 또는 전체 유지를 미리 가정하지 않는다.

## 말풍선 데이터 확장

- 2026-11-26 사용자 지정: [머리 위 말풍선](../game-design/experience/interface.md#머리-위-말풍선-대사) 관련 데이터는 언제든 쉽게 추가할 수 있는 구조로 준비한다.
- 대사 콘텐츠와 표시 처리를 분리해, 기존 기능 안의 대사 항목 추가·수정은 표시 코드를 고치지 않고 데이터 편집으로 할 수 있게 설계한다. 주인공·조수·일반 생명체가 같은 추가 절차를 이용할 수 있게 한다.
- 데이터 형식·편집 경로·필드·조건 연결 방식과 검증 방법은 해당 기능 개발 때 정한다. 쉽게 추가한다는 요구만으로 실행 중 실시간 반영 기능이나 전용 편집 도구 도입을 확정하지 않는다.
- 구현 검수에서는 기존 표시 코드를 수정하지 않고 대사 항목을 추가해 대상에 표시하는 과정을 확인한다. 새 기능이나 새 발생 조건이 필요한 확장은 별도 설계한다.

## 생명체 설명 데이터 관리

- 2026-11-26 사용자 지정: [생명체 설명과 관찰 기록](../game-design/experience/narrative.md#생명체-설명과-관찰-기록)을 데이터로 관리하며 수정·추가·삭제를 쉽게 한다.
- 설명 콘텐츠와 표시 처리를 분리해 기존 표시 코드를 수정하지 않고 데이터 편집으로 항목을 관리할 수 있게 설계한다. 설명 항목의 삭제는 생명체 정의나 게임 속 개체의 삭제를 뜻하지 않는다.
- 제품 문구는 [Localization 지침](localization.md)에 따라 주제별 CSV와 번역 키로 관리한다. 설명 항목과 생명체의 연결 구조·필드·편집 절차는 해당 기능 개발 때 정한다.
- 삭제 시 연결된 참조와 번역 키 사용 여부를 확인하는 절차를 마련한다. 구현 검수에서 항목 추가·내용 수정·삭제 후 표시와 참조가 올바른지 확인한다.

## 연구 기록 데이터 관리

- 2026-11-26 사용자 지정: [연구 효과 설명과 연구 소견](../game-design/experience/narrative.md#연구-효과-설명과-연구-소견)을 데이터로 관리하며 수정·추가·삭제를 쉽게 한다. 기존 표시 코드를 수정하지 않고 콘텐츠 데이터를 편집해 관리할 수 있게 설계한다.
- 제품 문구는 [Localization 지침](localization.md)의 주제별 CSV와 번역 키로 관리한다. 연구 항목과 설명·소견의 연결 구조와 편집 절차는 해당 기능 개발 때 정한다.
- 설명·소견의 편집과 실제 연구 효과·해금 규칙의 변경을 구분한다. 설명 항목 삭제로 연구 정의나 저장된 연구 진척을 삭제하지 않는다.
- 구현 검수에서 항목 추가·내용 수정·삭제 후 표시와 참조를 확인한다. 삭제 전 연결된 참조·번역 키 사용 여부를 확인하고, 효과 설명이 실제 연구 결과와 일치하는지 검수한다.

## 판단과 명령

- [커맨더](../game-design/systems/commanders.md)의 판단 방식을 교체할 수 있도록 필요한 추상화를 적용한다.
- 커맨더는 상태 조회 후 게임 내부의 공통 명령 API로 작업 우선순위·배정을 조정한다. 외부 AI 서비스 도입을 의미하지 않는다.
- 상태 조회·판단·명령 검사·작업 실행을 구분한다. 공통 유효성 검사와 실행 로직을 커맨더별로 복제하지 않는다.
- 집계 공유·판단 주기·캐시·변경 대상만 갱신하는 방식을 검토한다. 중앙 판단이나 복잡한 알고리즘만으로 성능·효율 개선을 단정하지 않는다.
- 실제 동률 처리·평가식·자료구조는 확정한 게임 규칙 안에서 정한다.

## 발광 표현과 최적화

- 2026-11-26 사용자 지정: [아트 디렉션의 발광](../game-design/experience/art-direction.md#lighting-and-glow)을 개발할 때 **개발 시점의 최신 Unity 공식 문서를 확인하고 최적화에 최대한 신경 쓴다.** 프로젝트의 Unity·렌더 파이프라인·패키지 버전과 문서의 적용 범위도 대조한다.
- 필요한 작은 발광 표현을 충족하는 구현 후보의 비용을 비교하고, 실제 장면에서 CPU·GPU·메모리 영향을 측정해 선택·조정한다. 구체 방식은 개발 시 결정하며 이번 기획 합의만으로 특정 조명·후처리 기능을 채택하지 않는다.
- 확인한 문서 URL·버전·확인일, 구현 선택 근거와 측정 결과는 해당 개발 PLAN에 남긴다. 검증 실행 범위는 [검증 지침](verification.md)을 따른다.

## 연결과 검증

- 생명체의 행동·대기 이유·명령 결과를 화면과 하네스에서 관찰할 수 있게 한다.
- 자동 전투는 작업 중단·운반물·예약·시설 피해·저장·일상 복귀와 함께 검증한다. 플레이어 전투 명령은 만들지 않는다.
- 공수 추정은 확정 일정이 아니다. 구현·검수 결과로 갱신하며 에이전트 사용에 따른 속도를 보장하지 않는다.
- 일반 검증과 별도 승인이 필요한 빌드·고부하는 [검증 지침](verification.md)을 따른다.
