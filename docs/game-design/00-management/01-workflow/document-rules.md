# 기획 문서 관리 규칙

- 갱신일: 2026-10-26
- 근거: 사용자 문서 정리 요청 및 D-002~D-004·D-010·D-011·D-035·D-059
- 탐색: [기획 MAP](../../README.md)

## 문서별 역할

| 문서 | 담당 역할 |
| --- | --- |
| README | 7개 필수 묶음과 기존 분류를 연결하는 MAP, 기획·개발 상태, 읽기 순서 |
| 각 주제 문서 | 해당 주제의 현재 유효한 규칙과 개발 위임 범위 |
| 구현 계획 | 전체 작업 순서·참조 문서·완료 기준·요약 상태와 PLAN 연결 |
| [에이전트 지침](../../../../AGENTS.md) | 작업 절차·Unity 변경·하네스·검증 방법 |
| [작업 PLAN](../../../plans/README.md) | 작업 단위별 상태·진행·다음 행동·실제 검증과 증거 |
| [기술 결정](../../../decisions/README.md) | 개발 위임 안의 주요 구현 선택·이유·대안·적용 위치 |
| 결정 기록 | D-ID별 승인 요약·현재 효력·명시적인 대체 관계와 기준 문서 링크 |
| 출처 | 승인 근거와 자료의 확인 한계 |
| 남은 사항 | 사용자 확인이 필요한 내용·개발 위임·후속 개발의 구분 |

현재 구현 규칙은 주제 문서에서 읽는다. 승인 범위나 충돌을 확인할 때 결정과 출처를 조회한다. 대체된 결정은 구현 요구사항으로 사용하지 않으며, 번호가 큰 결정이 무조건 모든 이전 결정을 무효화한다고 해석하지 않는다. 부분 변경이면 명시적으로 대체한 부분만 변경한다.

## 유지할 구조와 식별자

- 기존 대분류·중분류 번호 폴더와 소분류 파일 경로를 유지한다. README의 필수 1~7은 기획 묶음이며 폴더 번호와 구분한다.
- 기존 문서 ID·D-ID·Q-ID·S-ID를 다른 의미로 재사용하지 않는다. ID별 근거를 확인할 수 있도록 링크를 유지한다.
- 주제 문서에는 문서 ID·분류·상태·검색어·근거·갱신일·MAP 링크를 둔다. 실제 남은 질문이 있을 때 관련 Q-ID를 연결한다.
- 현재 규칙은 담당 문서 한 곳에 상세히 작성한다. 다른 문서에는 연결에 필요한 짧은 설명과 링크를 둔다.
- 폐기된 규칙 전문, 해결된 질문의 반복 설명, 당시 진행률·다음 논의 안내는 삭제한다. 결정 기록에는 현재 효력과 대체 관계를 최소한으로 남긴다.
- 후속 개발 계획과 개발 위임 항목은 폐기된 기획으로 취급하지 않는다.

## 상태와 변경 기준

| 상태 | 의미와 처리 |
| --- | --- |
| 확정 | 사용자가 지정하거나 승인한 현재 규칙. 구현의 기준으로 사용한다. |
| 개발 위임 | 확정 규칙 안에서 구현하며 선택·조정할 상세. 매번 사전 승인을 요구하지 않는다(D-059). |
| 확인 필요 | 승인 근거가 부족한 사항. 현재 확정 규칙에 없는 내용을 추정하여 구현하지 않는다. |
| 미정 | 사용자가 아직 정하지 않았다고 명시한 사항. |
| 후속 개발 | 이번 프로토타입 밖의 범위. 완료 조건에 포함하지 않는다. |
| 제안 | 검토 중인 후보. 승인된 규칙과 구분한다. |
| 대체·부분 대체 | 이전 결정의 효력 상태. 현재 규칙과 대체 결정으로 안내한다. |

새 핵심 게임 규칙·콘텐츠 범위·완료 기준을 바꿀 때는 한 항목씩 논의하고 사용자 승인 후 반영한다. 승인되면 담당 주제 문서·결정 기록·필요한 질문 상태와 MAP을 함께 갱신한다. 개발 위임은 핵심 규칙을 임의로 바꾸는 권한이 아니다.

## 에이전트의 개발 절차

1. [에이전트 작업 절차](../../../agents/workflow.md)에 따라 유일한 active PLAN을 확인하고 [구현 계획](../../05-development/02-implementation/roadmap.md)에서 단계와 완료 기준을 조회한다.
2. 해당 단계의 기준 문서만 우선 읽고, 연결된 다른 시스템의 규칙을 필요한 만큼 참조한다.
3. 이미 확정된 규칙은 유지한다. 실제 핵심 공백·충돌이 있으면 질문하고, 위임된 클래스·API·수치·화면 상세는 개발하며 결정한다.
4. 작은 구현 선택은 해당 PLAN에, 주요 기술 선택은 docs/decisions에 기록한다. 사용자 승인 기획과 구분하고 상태와 연결 관계의 검증은 해당 구현 단계에서 함께 진행한다.
5. 실제 검증과 증거는 해당 PLAN에 남기고 전체 단계가 바뀌면 구현 계획에 요약과 PLAN 링크를 반영한다. 설계 승인·도구 설치·연결만으로 구현 또는 테스트 통과를 표시하지 않는다.

게임 하네스의 구조는 [Thing과 정의 데이터](../../05-development/01-architecture/thing-model.md), 도구와 실행 환경은 [플레이 환경](../../04-delivery/01-platform/environment.md)을 따른다. 문서 참조와 게임 실행 검증을 구분한다.

## 프로토타입과 기획 완료

1차 목표는 제한된 콘텐츠로 게임 사이클을 충분히 반복할 수 있는 프로토타입이다(D-010·D-011). 핵심 규칙·범위·검증 방법을 승인하고 나머지 상세를 개발 위임으로 구분하면 1차 기획 완료다(D-035·D-059). 모든 후속 기획과 수치를 먼저 확정할 필요는 없다.

실제 프로토타입 완료는 [최초 제공 범위](../../04-delivery/02-release/scope.md)의 완료 기준으로 판단한다. 기획 완료와 구현·검증 완료를 구분한다.
