## 초기 상태와 개발 값

[LaboratorySessionFactory](../../UnityProject/Assets/Scripts/Gameplay/Session/LaboratorySessionFactory.cs)가 실제 신규 세션을 만든다. 진단 장면의 초기 구성을 재사용하지 않는다.

| 항목 | 이번 단계의 개발 초기값 |
| --- | --- |
| 공간 | 16×10, 시작 개체 위치 (1,1), 선배치 시설 없음 |
| 시작 지급 | 프로토타입의 보관 컴포넌트에 유기물 4개. 지급량은 획득시설 비용 + 저장소 비용으로 계산 |
| 시설 건설 | 두 시설 각각 유기물 2개, 실제 건설 작업 3초 |
| 시설 크기·상호작용 위치 | 획득시설 2×2·로컬 (0,-1), 기존 저장소 3×2·로컬 (1,-1). 회전은 공통 Map 기하 계산을 사용 |
| 저장·이동 | 저장 용량 20, 개체 운반량 5, 직교 한 칸 이동 0.25초 |
| 작업 | 한 시설의 실제 건설·수집 작업자는 1개체. 운반은 시설 전체가 아닌 수량 예약 |
| 우선순위 | 건설 1·수집 2·운반 3, 작은 양수 우선·0 비활성. 동률은 이 목록 순서 |

수집 5개/실제 5초는 승인된 기획값이다. 나머지 값은 이 단계의 구현·검증용 초기값이며 최종 밸런스나 새 콘텐츠 제한이 아니다.
초기 자원을 이미 존재하는 개체가 보유하여 첫 저장소 없이도 건설할 수 있다. 숨은 창고·바닥 아이템·추가 지급을 도입하지 않는다.
건설 자원은 고정 상호작용 위치에 전달될 때 소비하고 `Delivered`에 기록한다. 이 기록은 재고가 아니며 실제 자원과 중복 집계하지 않는다.
미완성 시설은 확정 위치를 점유하지만 재료와 건설 작업을 모두 마치기 전에는 수집·저장 기능을 사용할 수 없다.
시설 종류·위치 선택을 제한하는 해금·강제 건설 순서·철거/환불 기능은 추가하지 않는다.

## 상태와 실행 책임

| 담당 | 원본 상태와 책임 |
| --- | --- |
| SO 정의 | 시설 역할·건설 비용/시간·출력/용량, 생명체 운반량/이동 시간 |
| Thing·Registry | 식별·생성 순서·단일 자원 소속, 자원 묶음의 부분 이전·합치기 |
| 시설 컴포넌트 | 건설 전달량/진행/완성, 수집 진행/미입고 완료품 수, 저장 허용 설정 |
| 개체 컴포넌트 | Job의 종류/단계/참조/수량/회차 출처, 이동 진행, 기본/개별 우선순위 |
| WorkerSystem | 작업 선택, 실제 이동·건설·수집. 작업 진행도는 시설에 남김 |
| LogisticsSystem | 출고·입고 예약, 수령·입고·부분 운반, 변경 예외·보유 대기 |
| LaboratorySimulation | 세션 안의 시스템 연결, 건설 후보·설정 명령, 상태 검사 |
| GameFlow | 단계·편집/앱 정지·저장 시점, 현재 세션으로 명령 전달 |

Gameplay 컴포넌트 부착 함수를 Registry에 주입한다. Core가 Gameplay 클래스나 공통 게임 작업 목록에 의존하지 않는다.
코드는 역할/기능 폴더로 분리하며 기존 Foundation 어셈블리와 GUID asmref를 사용한다. 폴더마다 별도 어셈블리를 만드는 방식은 현재 필요하지 않다.
일반 C# 실행 상태와 MonoBehaviour 화면을 분리한다. 화면·하네스가 같은 명령·Map·갱신을 사용한다.

## 이동·시간·회차

- 공통 Map의 시설 점유와 고정 상호작용 위치를 사용하는 4방향 BFS를 적용한다. 현재 작은 격자에서 최단 거리와 동률 재현을 확인하기 쉽다.
- 경로는 파생 정보로 재계산하며 저장하지 않는다. 시작 칸이 시설 아래에 있으면 인접한 빈 칸으로 나올 수 있으나 막힌 다른 칸을 통과하거나 순간 이동하지 않는다.
- 실제 Update와 하네스 모두 SessionController의 시간 입력을 통과한다. 연구소 입력은 최대 0.05초의 작은 단계로 나누며 이동에 쓴 시간을 같은 단계의 작업에 다시 쓰지 않는다.
- 시설 배치 후보 중에는 연구소 갱신을 멈춘다. 확정 후 변경된 공간에서 예약/Job을 재검사한 뒤 다음 시간 입력을 처리한다.
- 수집 완료품은 시설 보관처에 생성한다. 집기와 실제 입고를 구분하고 `Outstanding`은 실제 저장소 입고량만큼 줄인다.
- 부분 운반과 대체 저장소 입고 중에도 회차 출처를 보존한다. 전량 입고되어 Outstanding이 0이 된 뒤 수집 진행을 새 회차로 초기화한다.

## 자원과 예약

예약은 실물 재고가 아니며 작업자·공급처·목적지·자원 묶음·수량·집기 여부·목적·수집 회차 출처를 연결한다.
예약량을 제외한 가용 재고/공간으로 선택하고 실제 수령 시 자원 소속을 개체로, 입고 시 저장소로 옮긴다.
분할은 원본의 남은 수량을 유지하고 새 묶음에 새 ID를 부여한다. 전체 이전은 기존 ID를 유지한다.
합치기는 같은 정의·보관처의 묶음만 허용한다. 물류는 다른 작업이 참조한 묶음을 제거하지 않도록 예약을 확인한다.
정상 운반은 집기 전 이동부터 유지한다. 경로·시설·허용 목록 변경 예외와 제외 재고 재배치는 기준 물류 문서를 따른다.
입고할 곳이 없어진 보유 자원은 개체에 남기며, 유효 목적지를 다시 찾는다. 바닥 투하나 임의 삭제로 해소하지 않는다.

## 저장 v2와 진단 호환

- 실제 플레이는 `runtimeKind: laboratory`와 버전 2로 건설·수집·Job·보유 자원·예약·설정을 저장한다. 슬롯은 `Application.persistentDataPath/Gameplay/session.json`이다.
- 기존 진단 저장 v1은 런타임 컴포넌트 없이 그대로 복원한다. 공유 SO에 새 역할 필드가 생겨도 기존 진단 세션을 실제 게임으로 변환하지 않는다.
- 실제 플레이 화면은 laboratory 계약을 요구한다. 진단 v1을 실제 플레이 슬롯에 놓으면 로드 오류를 표시하고 파일을 덮어쓰지 않는다.
- JsonUtility의 중첩 null 표현에 의존하지 않도록 컴포넌트/Job 존재 여부를 명시한다. ID·소속·진행 범위·예약 합계·회차 잔량을 새 객체 그래프에서 검증한다.
- 모든 검사를 통과한 후보만 현재 세션으로 교체한다. 임시 건설 후보·선택·경로·대기 문구는 저장하지 않으며 확정 상태에서 다시 계산한다.
- 재시작은 실제 초기 구성을 새 객체로 만들고 파일 교체에 성공한 뒤 반영한다. 쓰기 실패 시 현재 상태와 마지막 정상 파일 보존은 TECH-004를 따른다.

## 화면과 적용 범위

[LaboratoryView](../../UnityProject/Assets/Scripts/Presentation/Gameplay/Laboratory/LaboratoryView.cs)는 PC 가로 화면에서 건설·배치·설정과 작업/진행/재고/예약/대기 이유를 표시한다.
`Temp_Laboratory` 씬의 임의(Temp) 표현은 Unity 기본 도형·문자이며 새 Sprite를 생성하지 않는다. 정식 아트·모바일 터치·세로 UI를 완료한 것으로 보지 않는다.
검증은 실제 신규 시작과 격리된 복수 개체/시설 검사 상태를 구분한다. 후자의 준비 데이터를 실제 무료 건설이나 추가 시작 개체로 노출하지 않는다.
구현·검증 진행과 실제 통과 수·로그·화면 증거는 PLAN-008 한 곳에 기록한다. 이 기술 결정의 작성 자체는 검증 완료를 뜻하지 않는다.
